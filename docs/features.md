# 功能总览与典型流程

这篇回答三个问题：**有哪些功能、各自解决什么问题、怎么用**；以及它们在真实场景里怎么串起来。名词定义见 [核心概念](concepts.md)，逐页说明见 [使用指南](user-guide.md)。

## 一、功能一览

| 功能 | 解决什么问题 | 入口 | 怎么用 | 是否调用模型 |
|---|---|---|---|---|
| 员工与角色 | 组一支分工明确的 AI 团队 | 公司 → 员工；项目 → 成员 | 新建员工、选模型和能力上限，加入项目时指定角色 | 否 |
| 目标与约束 | 让所有员工朝同一个方向 | 计划 → 项目目标 | 写技术栈、不做什么、验收标准；AI 只能提议修改，你批准 | 否 |
| 需求 | 记录「做什么 + 怎么做」，迭代时有据可查 | 需求 | 提交业务面 + 技术面（可指定技术方案）；直接采纳或进需求池 | 采纳后写规格时调用 |
| 计划 | 把目标/需求拆成有依赖、有等级的条目 | 计划 | 让负责人起草，或手动加条目；看每个条目在等什么 | 起草时调用 |
| 排期 | 决定先做什么、什么时候回来修 bug | 排期 | 自动：有未排期且有人空闲时负责人排一次；手动：上移下移、退回、请负责人排期 | 有未排期时调用一次 |
| 自主推进 | 长时间少打扰地推进整个项目 | 职责 | 设批次预算，点「开始自主推进」；可自动续批次 | 是（员工与负责人的工作） |
| 任务与合并 | 并行开发不互相踩，改动可追溯 | 任务 | 每个任务一个 worktree + 分支；验证、评审后合并；可放弃（留 WIP） | 是 |
| 评审门 | 大改动必审、小改动不浪费 | 自动 | 按规则判断，必要时让负责人看 diff | 视情况 |
| Bug | 上线后问题有单独的生命周期 | Bug | QA 自动记，你也可手动添加；系统自动建修复 + 复测条目 | 记录/建条目不调用 |
| 定时器 | 周期性检查不靠人记 | 定时器 | 勾选预置任务启用；对齐会在这里配置 | 对齐会调用 |
| 议题与裁决 | 有分歧时有人拍板 | 议题 | 员工提议，AI 负责人裁决；升级给你时在这里处理 | 是 |
| 评审意见 | 评审里的问题不丢 | 评审意见 | `[合并前]` 拦合并；`[之后再说]` 自动成未排期条目 | 否 |
| 对齐会与会议 | 防止多个 AI 久了跑偏 | 会议、定时器 | 定期开对齐会；也可以自己发言 | 是 |
| 记忆 | 经验沉淀，新任务带上 | 记忆 | 查看、编辑、确认；公司/项目/个人三层 | 整理时调用 |
| 文档 | 项目背景与需求规格随时间演进可追溯 | 文档 | 项目文档（固定五份）+ 规格文档；每份有 git 版本列表和 diff | 更新文档时调用 |
| 公司总览 | 多个项目一眼看谁需要你 | 公司 → 总览 | 看完成度、bug、未排期、待评估需求和「需要关注」的原因 | 否 |
| 人工介入中心 | 不漏掉需要你的事 | 右上角铃铛 | 审批、议题、卡住提示都汇总在这里 | 否 |
| 本地模型 | 让简单活不占订阅额度 | 模型 → 自建端点 | 配 Ollama 等端点，给员工选；见 [连接本地模型](endpoints.md) | — |
| 用量 | 看清花了多少 | 用量 | 按员工/模型/用途汇总 | 否 |

## 二、功能之间怎么触发

```
提交需求 ──采纳──▶ 规格条目（架构师/开发写 requirements.md + design.md）
                      └─定稿─▶ 负责人拆实现条目（指向规格，按 AC-n 验收）──▶ 未排期

QA 记 Bug ──▶ 修复条目（原开发）+ 复测条目（QA/负责人，依赖修复）──▶ 未排期
定时器到点 ──▶ 检查条目 ──▶ 未排期
评审 [之后再说] ──▶ 条目 ──▶ 未排期

未排期 + 有人空闲 ──▶ 负责人排期（一次处理全部）──▶ 已排期
已排期 + 前置完成 + 人空闲 + 预算够 ──▶ 派活 ──▶ 任务 ──▶ 验证 ──▶ 评审门 ──▶ 合并
合并 ──▶ 更新文档（git 版本 +1）；议题裁决 ──▶ 决策文档；设计要点 ──▶ 项目记忆
```

记住一条主线：**所有新活先进未排期，排期决定顺序，自主推进只派已排期的。**

## 三、典型流程

### 1. 新项目从零开始
1. 公司 → 新建员工（负责人、开发、QA，最好有架构师）。
2. 新建项目选 git 仓库，成员页加入员工并指定角色。
3. 计划页写目标，让负责人起草计划（有架构师会先出设计条目）。
4. 职责页设预算，点「开始自主推进」。
5. 平时看群聊、计划、任务；铃铛提示时处理。

### 2. 已有代码的老项目接手
1. 新建/导入项目，目录有代码会自动勾「已有项目」。
2. 导入页：只读扫描 → 测试基线 → 你确认，之后才让员工动代码。
3. 之后同流程 1；老项目的改动多从「需求」和「Bug」进入。

### 3. 上线后发现 Bug
1. QA 在测试中自己记；你发现的在 Bug 页点添加（填严重程度、复现步骤、期望与实际行为）。
2. 系统立刻生成修复条目（原开发）+ 复测条目，都在未排期。
3. 下次有人空闲，负责人把它们排进去——P0 通常插最前。
4. 开发修完 →「待复测」→ QA 复测通过才「已关闭」；没通过点「重开」。
5. 要自己定优先级或换人，在 Bug 页直接改。

### 4. 需求迭代
1. 需求页提交：业务面（做什么、验收标准）+ 技术面；有明确技术方案就填「人指定的技术要求」。
2. 勾「直接采纳」立刻开始；不勾则进需求池，等负责人排期时评估（采纳/搁置/拒绝要写原因）。
3. 架构师写 `requirements.md` 和 `design.md`，定稿后负责人拆实现条目。
4. 需求变了点「修订」：员工在原文档上改并追加变更记录，只为变化的部分拆新条目。
5. 文档页看规格的版本列表，点一行看那次改了什么。

### 5. 长期运转
- 在「定时器」启用你需要的检查类任务，到点自动生成条目。
- 在「职责」开自动续批次，应用重启后会自动接着做。
- 每天看一眼「公司 → 总览」，只处理标了「需要关注」的项目。

## 四、什么时候该自己出手

| 情况 | 你该做 |
|---|---|
| 铃铛有审批 | 允许 / 拒绝 / 允许并加白名单 |
| AI 提议改目标 | 在计划页批准、修改后批准或驳回 |
| 批次提示「等你处理」 | 看原因，处理后「再开一个批次」 |
| 排期不合你意 | 上移下移、退回未排期 |
| 某条目卡住 | 看计划页等待原因；必要时放弃任务重派 |
| 要装新版本 | 先确认没有员工在干活（`./scripts/install-mac.sh` 会重启应用并打断他们） |

## 五、边界

- 仅 macOS；员工引擎目前只有 Claude Code 和 GitHub Copilot CLI。
- 早期版本，界面没有在所有场景下验证，没有前端测试。
- 排期、Bug 自动记录、规格遵循等行为，在真实模型下的稳定性取决于所用模型；负责人建议用能稳定输出 JSON 的模型。每个功能验证了什么、没验证什么见 [target.md](target.md) 第 20 章。
