# AI Development Studio
## 本地 AI 研发团队工作台
### 产品需求与技术架构说明书（初始版本）

- 文档版本：0.1
- 产品形态：macOS 本地桌面客户端
- 核心技术：Rust
- UI 候选：Tauri 2
- 产品定位：面向个人开发者和小型研发团队的多 AI 员工协作、项目管理与软件工程工作台
- 当前阶段：架构设计与开发准备

---

# 1. 产品愿景

开发一款类似 CC Switch 的 Rust 本地桌面客户端，但它不只是 AI 模型或账号切换工具，而是一个完整的本地 AI 软件研发团队工作台。

用户可以在客户端中创建 AI 员工、分配 AI 账号、管理项目、组织团队讨论，并让 AI 员工通过原生 CLI 工具完成需求分析、架构设计、代码开发、测试、Bug 修复和文档维护。

产品的核心目标是：

**让少量具备全栈能力的 AI 员工，像真实的软件工程师团队一样长期协作。**

用户本人负责提出产品需求、确定业务方向、参与架构讨论、审批关键决策。

AI 员工负责：
- 分析需求并提出疑问。
- 讨论技术方案并提出不同意见。
- 制定开发计划。
- 实际编写代码。
- 运行测试和修复问题。
- 进行代码审查。
- 维护项目文档。
- 沉淀长期工程经验。
- 在后续项目中复用经过验证的经验。

产品既支持从零创建新项目，也必须支持导入已有项目并进行二次开发、重构和迁移。

# 2. 核心设计原则

## 2.1 少角色、全栈能力

不采用大量专业岗位组成的复杂 Agent 组织。

核心团队保持精简：

- 人类 CTO / 架构师（可选，由用户担任）。
- AI 全栈工程师 A。
- AI 全栈工程师 B。
- AI QA 测试工程师（可选）。

AI 全栈工程师需要具备跨前端、后端、数据库、接口、测试和部署的综合开发能力。

QA 可以是独立 AI 员工，也可以由其他 AI 员工承担交叉质检。

不应为了模拟真实公司而创建大量没有必要的 Agent。

## 2.2 员工、账号、会话相互独立

必须严格区分四个概念：

1. Employee：长期存在的 AI 员工身份。
2. Account / Provider：实际使用的模型服务账号和执行工具。
3. Project Session：员工在某个项目中的独立工作会话。
4. Execution Instance：实际启动的 CLI 进程或一次任务执行实例。

员工身份不应该与某个 Claude 账号永久绑定。

员工可以更换执行引擎，但其个人经验和身份不应因此丢失。

同一个员工可以参与多个项目，每个项目拥有独立会话和上下文。

## 2.3 原生 CLI 优先

优先使用官方 CLI，而不是自行实现模型 API 协议或重新实现 Agent。

第一阶段重点支持：

- Claude Code CLI
- GitHub Copilot CLI

后续可以扩展：

- OpenAI Codex CLI
- Gemini CLI
- 其他兼容的 Coding Agent

Rust 客户端负责：
- 账号配置和管理。
- CLI 进程启动与监控。
- 会话管理。
- 工作目录和 Git 隔离。
- 任务分配。
- 员工协作。
- 记忆管理。
- 审批与权限。
- 成本和执行情况统计。

尽可能保留官方 CLI 自身的 Agent 能力。

需要优先研究 CLI 的官方自动化接口、JSON/流式输出、会话恢复、工具权限和退出状态。避免依赖脆弱的终端文本解析或模拟键盘操作。

# 3. 团队组织模式

产品支持三种组织配置。

## 模式 A：人类 CTO + 两个全栈工程师 + 独立 QA

推荐用于复杂系统。

- 人类：需求确认、架构决策、重大技术争议裁决。
- AI 全栈 A：承担项目开发任务。
- AI 全栈 B：承担并行开发任务。
- AI QA：独立测试、代码审查、回归验证。

## 模式 B：AI CTO + 一个全栈工程师 + 独立 QA

适合人类主要负责业务需求、AI 负责技术决策和执行的项目。

- AI CTO：需求分析、架构规划、任务分配、项目文档。
- AI 全栈：实际开发。
- AI QA：测试和质量验证。
- 人类：参与讨论、确认重要决策和高风险操作。

## 模式 C：AI CTO + 一个全栈工程师 + 交叉质检

适合预算敏感或规模较小的项目。

- AI CTO：规划和架构。
- AI 全栈：开发。
- 交叉质检：通过独立审查会话检查开发成果。

必须避免开发者仅仅重复自己的结论就被视为独立审查。

QA 角色可以独立存在，也可以在需要时由其他员工临时承担。

项目负责人是一种项目职责，不必对应一个额外的 AI Agent。

# 4. 项目群聊与协作机制

这是产品的重要功能。

用户、AI CTO、全栈工程师和 QA 可以进入同一个项目讨论空间。

所有成员可以：
- 直接讨论技术方案。
- 对其他成员的观点提出异议。
- @指定员工。
- 要求员工重新分析。
- 请求其他员工进行代码审查。
- 讨论 Bug 和解决方案。
- 请求人类 CTO 裁决。
- 查看任务、开发和测试状态。

群聊不应该采用完全单向的流水线：

用户 → CTO → 工程师 → QA → CTO → 用户。

应该允许成员直接沟通。

## 4.1 按需唤醒 Agent

不能每条群消息都唤醒所有 AI 员工。

以下情况才触发对应 Agent：
- 被 @。
- 被明确分配任务。
- 被要求发表意见。
- 任务状态发生需要其处理的变化。
- QA 发现需要开发者处理的问题。
- 人类 CTO 发起讨论。
- 项目负责人要求汇总重要决策。

其他成员只记录事件，不产生无意义的模型调用。

群聊消息、任务事件、Agent 执行结果需要统一记录。

## 4.2 人类确认机制

Claude Code 在实际开发中可能要求人类确认工具操作，也可能在遇到不确定问题时提出问题。

产品应保留人类介入能力。

至少支持：
- AI 请求确认。
- AI 提出多个方案供人类选择。
- 人类要求重新分析。
- 人类否决当前方案。
- 人类指定新的技术方向。
- 人类暂停或终止任务。
- 人类批准高风险操作。

AI 不能因为某个方案已经执行了一半，就把它视为必须继续的方案。

# 5. 员工与账号管理

## 5.1 员工管理

每个员工拥有：
- 唯一员工 ID。
- 员工名称。
- 岗位类型。
- 身份说明。
- 能力和技能。
- 工作偏好。
- 关联的个人记忆。
- 参与过的项目。
- 历史任务。
- 当前工作状态。
- 当前执行引擎配置。

员工身份独立于模型账号。

## 5.2 账号管理

第一阶段目标配置：

- Claude 订阅账号 A。
- Claude 订阅账号 B。
- GitHub Copilot 账号。

但必须先验证多个订阅账号是否能在 macOS 上稳定并行运行。

Claude Code 的 CLAUDE_CONFIG_DIR 可以隔离部分配置和会话数据，但不能直接假设它一定能解决 macOS Keychain 凭证隔离问题。

需要进行独立技术验证：
1. 两个不同配置目录分别登录不同 Claude 账号。
2. 同时启动两个 Claude Code 进程。
3. 两个进程分别调用模型。
4. 测试 OAuth Token 刷新。
5. 关闭并重启客户端。
6. 验证账号没有相互覆盖。
7. 验证两个账号可以恢复各自会话。

不得通过绕过官方认证机制或违反服务条款的方式实现多账号隔离。

如果双账号并发无法稳定实现，第一版必须支持单账号多个独立会话。

同一账号的多个并行进程会共享该账号的使用额度，不能假设创建更多员工就获得更多订阅额度。

## 5.3 执行引擎抽象

建议建立 Provider / Runtime Adapter 接口。

每种 CLI 作为独立适配器。

统一处理：
- 启动。
- 登录状态检测。
- 进程生命周期。
- 会话创建和恢复。
- 标准输入与输出。
- 流式事件。
- 执行状态。
- 错误处理。
- 退出状态。
- 权限和工具审批。

不要让业务代码直接依赖 Claude Code 的内部实现。

# 6. 项目管理

支持两种项目入口：

1. 新建项目。
2. 导入已有项目。

项目是所有员工协作的基本边界。

一个项目应包含：
- 项目名称和描述。
- 本地路径。
- Git 仓库信息。
- 技术栈。
- 项目架构。
- 参与员工。
- 项目负责人。
- 项目会话。
- 项目公共记忆。
- 技术决策。
- Bug 和测试记录。
- 开发计划。
- 任务和交付记录。

# 7. 旧项目导入（Project Onboarding）

旧项目接管是核心能力，不能作为附属功能。

用户可以选择本地项目目录或 Git 仓库。

导入时默认先进行只读分析。

## 7.1 自动识别

识别：
- 编程语言。
- 前后端框架。
- 数据库。
- 依赖和包管理器。
- 构建工具。
- 测试框架。
- 项目目录结构。
- Git 分支和提交历史。
- CI/CD 配置。
- API 定义。
- 数据库 Schema。

## 7.2 项目地图

通过代码分析和 AI 辅助，建立：
- 模块结构。
- 模块依赖关系。
- 主要调用链。
- API 和接口关系。
- 数据库表及关系。
- 重要业务流程。
- 核心配置和环境变量说明。
- 项目运行和部署方式。

项目地图应该能够增量更新，而不是每次重新分析整个项目。

## 7.3 建立项目基线

导入时尝试执行：
- Build。
- Unit Tests。
- Integration Tests。
- Lint。
- 静态检查。
- 安全扫描。

记录原始结果。

特别注意：已有项目可能存在原始测试失败、历史 Bug 和技术债。

必须建立项目基线，区分：
- 导入前已经存在的问题。
- AI 修改引入的新问题。
- AI 修复后仍然存在的问题。
- 无法确认来源的问题。

不能把所有历史问题都归咎于 AI 的新修改。

## 7.4 AI 联合评估

全栈工程师负责分析架构、代码和技术债。

QA 负责分析：
- 测试覆盖率。
- 潜在缺陷。
- 兼容性问题。
- 安全风险。
- 缺少的回归测试。

最终形成：
- 项目概览。
- 架构文档。
- 技术栈报告。
- 模块地图。
- 测试基线报告。
- 技术债清单。
- 风险清单。
- 建议开发计划。

由人类确认后，项目正式进入 AI 团队维护阶段。

# 8. 新项目开发

新建项目流程：

1. 用户提出需求。
2. AI 分析需求。
3. AI 提出不明确的问题。
4. AI 提出架构和技术方案。
5. 团队讨论并提出不同意见。
6. 人类确认重大决策。
7. 项目负责人形成项目文档。
8. 拆分任务。
9. 全栈工程师开发。
10. CI 自动化测试。
11. QA 审查。
12. Bug 修复。
13. 回归测试。
14. 人类验收。
15. 沉淀项目经验。

# 9. Git 与并行开发

建议使用 Git Worktree。

每个员工在项目中的开发任务拥有独立工作目录和分支。

例如：

- project/main：主分支。
- project/employee-a：员工 A 的工作区。
- project/employee-b：员工 B 的工作区。
- project/qa：QA 的测试工作区（按需）。

要求：
- 不允许多个 Agent 无协调地同时修改同一工作目录。
- 明确任务的文件范围和模块边界。
- 支持提交、查看 Diff、创建 PR 或本地审查。
- 记录每次修改对应的任务和员工。
- 合并前执行必要测试。
- 冲突由 Agent 分析，重大冲突请求人类确认。

# 10. 任务与 QA 生命周期

任务至少包含：
- 待分析。
- 待确认。
- 待开发。
- 开发中。
- 待测试。
- 测试中。
- 测试失败。
- 待修复。
- 回归测试。
- 待验收。
- 已完成。
- 已取消。

Bug 至少记录：
- Bug ID。
- 所属项目。
- 严重程度。
- 复现步骤。
- 预期行为。
- 实际行为。
- 日志和错误信息。
- 相关文件。
- 责任任务。
- 修复方案。
- 修复提交。
- 回归测试结果。
- 最终状态。

QA 不应该每个开发步骤都重新理解整个项目。

应尽量通过自动化测试发现问题，仅在需要推理时才调用 QA Agent。

# 11. 长期记忆系统（Memory Manager）

记忆由 Rust 客户端统一管理。

第一版不应依赖 Claude Code 自带 Auto Memory 作为唯一长期记忆系统。

## 11.1 三层记忆

### 员工记忆

记录：
- 员工技能。
- 擅长领域。
- 历史经验。
- 工作习惯。
- 经过验证的解决方案。
- 曾经犯过的错误。
- 经验的适用范围。

### 项目记忆

记录：
- 项目架构。
- 技术栈。
- 模块地图。
- 接口约定。
- 技术决策。
- 业务规则。
- 已知问题。
- 风险。
- 历史变更。

### 任务记忆

记录：
- 当前任务。
- 目标和验收条件。
- 修改文件。
- 当前进度。
- 测试结果。
- 未完成事项。
- 交接信息。

## 11.2 记忆共享规则

员工个人记忆默认独立。

项目公共知识可以被所有项目成员检索。

员工可以学习其他成员的经验，但经验需要经过验证、整理和确认后才能进入个人长期记忆。

QA 的测试经验可以被全栈工程师检索。

全栈工程师的架构经验也可以被 QA 检索。

## 11.3 记忆检索

禁止每次请求都注入：
- 所有聊天历史。
- 全部项目文档。
- 所有员工记忆。
- 所有历史 Bug。

应该按当前任务检索少量相关内容。

建议第一版使用：
- SQLite。
- SQLite FTS5。
- 结构化 JSON/Markdown。
- 后续可增加向量检索。

## 11.4 经验质量

每条重要经验需要有：
- 来源。
- 所属项目。
- 创建时间。
- 验证状态。
- 适用范围。
- 相关代码或 PR。
- 是否已经过期。

不能让 AI 将一次未经验证的猜测永久写入知识库。

# 12. Token 与运行成本管理

成本控制是核心需求。

此前多 Agent 架构容易因为每个岗位重复启动 Claude Code、重复读取项目、反复传递完整聊天历史而产生大量 Token 消耗。

本产品必须在设计阶段解决这一问题。

## 12.1 核心原则

- 岗位数量不等于 Agent 调用数量。
- 群聊消息不等于模型调用。
- 自动化检查优先使用普通程序。
- 任务按需唤醒 Agent。
- 尽量复用合适的项目会话。
- 任务交接使用精简结构化数据。
- 只检索相关记忆。
- QA 按需介入。
- 避免无意义的多轮总结。

## 12.2 运行数据

记录：
- Provider。
- 账号 Profile。
- 员工。
- 项目。
- 会话。
- 任务。
- 模型调用次数。
- 输入/输出 Token（CLI 能提供时）。
- 使用额度或成本（能可靠获取时）。
- 执行耗时。
- 失败次数。
- 重试次数。
- 会话恢复情况。

不能把订阅套餐额度和 API 按 Token 计费混为一谈。

如果 CLI 不提供可靠 Token 数据，必须明确标记为未知，不能伪造精确数据。

# 13. 人工审批与安全

尤其考虑交易所、金融系统等高风险项目。

默认禁止未经人类明确批准：
- 操作生产环境。
- 使用真实资金。
- 创建或执行真实订单。
- 读取或导出生产私钥。
- 执行不可逆数据库迁移。
- 删除重要生产数据。
- 修改真实用户资产。
- 发布高风险版本。

建议建立权限等级：

1. 只读分析。
2. 本地文件修改。
3. 本地命令执行。
4. 测试环境操作。
5. Git 提交和合并。
6. 部署操作。
7. 生产环境及不可逆操作。

不同等级应有明确的审批规则。

人类审批不能只靠聊天中的一句模糊指令，应记录具体操作、目标和审批结果。

# 14. Rust 技术架构建议

建议模块划分：

- account：账号和 Profile 管理。
- runtime：CLI 进程管理。
- provider：Claude Code、Copilot 等适配器。
- employee：员工身份和技能。
- team：团队配置。
- project：项目管理。
- onboarding：旧项目导入。
- workspace：目录和 Git Worktree。
- session：项目会话管理。
- orchestrator：任务调度。
- event_bus：事件分发。
- chat：群聊。
- memory：长期记忆。
- knowledge：项目知识库。
- qa：测试和 Bug 管理。
- approval：权限和审批。
- telemetry：运行和成本统计。

建议技术：
- Rust。
- Tokio。
- SQLite。
- SQLite FTS5。
- Git Worktree。
- JSONL 事件日志。
- Tauri 2（如果采用桌面 UI）。

模块边界应保持清晰，避免所有功能集中在一个巨大的服务或状态管理对象中。

# 15. MVP 开发范围

# 20. 决策记录与 Phase 0 实测结果（v0.2，追加）

## 20.1 已确认决策

1. **账号**：MVP 只用一个 Claude 订阅账号。Account/Profile 抽象和外键保留，数据库中仍是 `employee → account_profile`，但只有一条记录。员工隔离靠独立会话、独立 worktree、独立记忆和系统提示词，不靠账号。多账号并发降级为可选实验，不阻塞。
2. **平台**：当前只实现 macOS，Windows 是未来事项。设计上不堵死：进程管理、Shell 执行、凭证存储各封装一层，业务代码不直接调用平台 API。
3. **技术栈**：Tauri 2 + TypeScript(React) 前端 + Rust 后端，参照 CC Switch。
4. **分层**：`core` crate 不依赖 Tauri，包含全部业务逻辑，可用命令行独立运行和测试；`app` crate 只做 Tauri command/event 桥接。TS 类型由 Rust 生成（specta 或 ts-rs）。
5. **调度**：全局并发上限（默认 2 个同时运行的 CLI）加排队，防止同一份额度被并行员工打满。
6. **Provider 顺序**：先做 Claude Code 适配器并跑通，再做 Copilot CLI，避免过早抽象。
7. **审批通道**：使用 Claude Code 的 `--permission-prompt-tool stdio`（见 20.2）。权限等级 MVP 先简化为三档：只读、工作区读写、需审批。
8. **事件流**：所有群聊消息、任务事件、Agent 输出、审批记录写入统一的追加式事件表（SQLite），同时落 JSONL。"按需唤醒"由 orchestrator 消费事件决定。
9. **崩溃恢复**：纳入 MVP。任务状态由事件日志重建，会话由 `--resume` 恢复。
10. **延后**：向量检索、项目地图增量更新、记忆验证流程的复杂规则、七级权限。

## 20.1.1 澄清：团队规模不设上限

文档中"AI 全栈 A / B""两个全栈"是举例，不是固定编制。团队可以是 1 个员工，也可以是 20 个甚至更多，员工数量不设上限。

由此带来的设计约束：

- 员工数量与同时运行的 CLI 进程数是两件事。所有员工共享同一份订阅额度，因此"并发上限"是独立的、可配置的调度参数（默认 3，可在界面调整），超出的任务进入队列，界面区分"工作中"和"排队中"。
- 员工是长期存在的身份（数据库中的一行），空闲员工不占用进程和额度。
- 界面和流程不能假设固定人数：员工列表需支持搜索，@ 提及需支持自动补全。
- Worktree 以"员工 × 任务"为单位按需创建，而非为每个员工固定预留目录。
- 议题、会议、审查的参与者按需选择，不默认全员参与。

## 20.2 Phase 0 实测结果（Claude Code 2.1.319，macOS）

| 项目 | 结果 |
|---|---|
| 程序化启动 | `claude -p --input-format stream-json --output-format stream-json --verbose` 可行，不需要 PTY |
| 指定会话 | `--session-id <uuid>` 创建，`--resume <uuid>` 恢复，已验证恢复后上下文保留 |
| 审批回传 | 加 `--permission-prompt-tool stdio` 后，权限请求以 `control_request`（`subtype: can_use_tool`，含 `tool_name`、`input`、`tool_use_id`）出现在 stdout；宿主向 stdin 写 `control_response`，`behavior` 为 `allow`（附 `updatedInput`）或 `deny`（附 `message`）。已验证 allow 后文件被写入 |
| 宿主断开 | stdin 提前关闭时，工具调用被拒绝并报 AbortError。因此 runtime 必须持续持有 stdin |
| 用量数据 | `result` 事件含 `total_cost_usd` 和 `usage`（input/output/cache token）；`rate_limit_event` 含 five_hour 与 seven_day 窗口的 `utilization`，可用于额度显示和调度限流 |
| 注意 | 每次启动会加载用户的 hooks 和插件（本机 SessionStart 钩子产生了额外输出）。生产环境应考虑 `--settings` 或隔离配置，避免员工会话被用户全局配置干扰 |

## 20.3 补充实测（macOS，Claude Code 2.1.319）

| 项目 | 结果 |
|---|---|
| 并发 | 3 个进程（3 个不同身份）同时运行，总耗时 4.3 秒，全部成功，无限流拒绝。未测更高并发 |
| 身份注入 | `--append-system-prompt` 有效，三个进程各自按身份回答，会话互不混淆 |
| 杀进程恢复 | 对进程组发 SIGKILL 后，用同一 `--session-id` 执行 `--resume`，上下文（暗号）保留。未测"工具调用执行到一半被杀"的情形 |
| 隔离全局配置 | `--safe-mode` 可用：保留登录和权限，关闭 hooks、插件、CLAUDE.md、skills、MCP。`--bare` 不可用：它跳过 keychain，订阅账号会显示未登录 |
| 单次开销 | 一次极短调用约 0.045 USD 等值（主要是系统提示词缓存写入），这是 CLI 报告的等值估算，不是订阅的实际扣费 |
| 额度信息 | `rate_limit_event` 返回状态；本机已出现 `allowed_warning`，说明额度告警可以被程序读取并用于调度 |

结论与影响：

- （已被 20.16 修正：不再使用 `--safe-mode`，因为它会关掉 MCP）员工进程统一使用 `--safe-mode`，由 Rust 自己注入身份、记忆和项目上下文，避免用户全局配置污染员工会话。
- 代价是项目自带的 CLAUDE.md 也会被关闭。导入旧项目时，需要由 onboarding 读取 CLAUDE.md 并在项目上下文中显式注入（待设计）。
- 并发上限先设默认 3，可配置，并根据 `rate_limit_event` 动态降级。

## 20.4 协作流程决策（v0.2，已确认）

1. 用户可在群里直接 @ 引入外部临时 AI（Guest），无需另走审批；成员或系统发起的引入仍需人类批准。Guest 默认只读、无个人长期记忆、只获得最小上下文，其结论经确认后才写入项目决策，会话限时过期。
2. 工作区读写默认允许，仅越权操作弹窗审批。
3. 人类只在里程碑验收，不逐任务验收，以节省 token 和时间。
4. 合并流程：自动检查通过 → 非作者的 AI 全栈审查 → 有问题在群里讨论 → 通过后由项目负责人最终确认并执行合并；负责人是人类时由人类合并。负责人自己写的代码，同样由其他 AI 全栈审查。
5. 流程图见 `docs/flows.md`。

## 20.5 群聊即会议室（v0.2，已确认方向）

1. 群是评审、站会、Code Review、需求评审、QA Case 评审、复盘的统一场所。会议 = 群话题 + 类型 + 纪要模板，不引入新机制。
2. 所有发言和 diff 写入事件表，全员可见；"旁听"不调用模型，只有被 @ 或点名的员工才被唤醒。
3. 每场会议结束由主持人（默认项目负责人）生成一份结构化纪要：决议、被否方案及原因、行动项、待验证经验。纪要写入项目记忆，并为相关员工生成摘要，在其下次唤醒时注入，而不是传递完整聊天。
4. 会上形成的经验标记为"待验证"，测试通过或合并后才转为"已验证"并可进入个人长期记忆。
5. 每场会议有最大发言轮数和 token 预算，超限强制收敛，交负责人或人类裁决。
6. Code Review 要求审查者先独立写意见，再查看他人意见，避免从众。
7. 站会由事件表自动汇总，模型仅做一次摘要。

## 20.6 议题板 Issue（v0.2，已确认方向）

1. 群内设议题板，公开给全体成员。议题（Issue）与任务（Task）、Bug 是三种不同对象：议题回答"需要讨论并决定什么"，解决后产生决策记录，并可关联生成任务或 Bug。
2. 字段：标题、问题摘要、类型、提出人、负责人、有权决定的人、状态、候选方案（含支持者与理由）、最终方案与决议原因（被否方案及原因保留）、关联的纪要/任务/Bug/提交、待验证经验。
3. 状态：待讨论 → 讨论中 → 待决策 → 已决议 → 实施中 → 已关闭；另有搁置、已取消。被推翻的决议不修改原记录，新建议题并标注"取代"。
4. 拍板权限按类型：一般技术方案由项目负责人；需求与业务方向仅人类；涉及资金、生产、不可逆操作、安全的仅人类；代码细节由负责工程师经审查人认可；Guest 无权拍板。AI 负责人遇到需求或高风险类议题，系统强制升级给人类。
5. 里程碑或项目结束时，由议题汇总生成决策记录（ADR 风格）和"已知问题与遗留风险"，经负责人确认后写入项目文档。
6. 员工被唤醒时只注入与自己相关的少量议题摘要，不注入整个议题板。

## 20.7 实现进展（命令行里程碑，v0.2）

已完成并在真实 Claude Code 上验证：

- 工程结构：Cargo workspace，`crates/core`（业务库，不依赖 UI）与 `crates/cli`（命令行入口）。Tauri 外壳尚未创建，待命令行链路稳定后加入。
- 存储：SQLite（employees / sessions / events）加 JSONL 事件日志，由 `PRAGMA user_version` 管理版本。
- Claude 适配器：stream-json 双向协议，`--safe-mode`，一轮任务一个进程，进程放入独立进程组。
- 策略：只读自动允许；工作区内写入与白名单命令默认允许；其余需人类审批；每次决策（含决策者是策略还是人类）写入事件。
- 并发：命令行层信号量限制并发（默认 3，`--max` 可调）；审批在终端串行提问。
- 恢复：会话停留在 `running` 即视为被中断；下次运行记录 `session_recovered`，用 `--resume` 接续，并提示 Agent 先核对工作区状态。
- 测试：14 个单元测试（策略、协议解析、数据库）；端到端实测通过两员工并发、审批允许、审批拒绝、强杀后恢复。

已知限制：
- 策略的路径判断是词法层面，不解析符号链接。
- 复合 Shell 命令（含管道、`$()`、循环）一律走审批，较保守。
- 尚未做 worktree、任务/议题/会议、记忆、Copilot 适配器。
- 额度读数显示 5 小时窗口已接近上限（约 86%），后续测试需控制用量；调度器尚未据此降速。

## 20.8 桌面外壳进展（v0.2）

## 20.9 Git Worktree 隔离（v0.2，已实现）

设计决策：

1. worktree 放在数据目录（`<数据目录>/worktrees/<仓库>/<员工>`），不放进项目仓库。放进仓库会让 Cargo 等工具向上找到用户自己的根配置而报错。
2. 每个员工在每个仓库一个持久 worktree，每个任务一个分支（`crewforge/<员工>/t-<任务ID前8位>`）。这样员工的 CLI 会话可以复用（`--resume` 依赖固定的工作目录），任务之间以分支隔离。员工名含特殊字符（如中文）时，目录与分支名退回到员工 ID 前缀。
3. 一个员工在一个仓库同一时刻只有一个进行中的任务；后续消息继续该任务，合并或放弃后才能开始新任务。
4. 每轮执行结束自动提交检查点，署名为该员工，提交信息带 `Crewforge-Task` 与 `Crewforge-Employee`，每处改动可追溯到任务和员工。执行被中断时同样保存为 WIP，进展不丢。
5. 合并使用 squash，一个任务在主分支上只留一个提交。合并前用 `git merge-tree` 预检冲突，不触碰任何工作目录。
6. 合并要求主工作区位于基础分支且没有未提交改动，否则拒绝，不会动用户正在编辑的文件。冲突时不做任何改动，任务保持进行中。
7. 放弃任务不删除任何内容：改动保存为 WIP 提交，分支保留。
8. 同一仓库的 git 写操作通过仓库级互斥锁串行；多个任务同时修改同一文件时，界面给出提示。
9. 合并动作目前由人类在界面确认（人类即项目负责人）。"非作者 AI 审查、负责人确认后合并"的流程待审查/会议功能完成后接入。

验证：数据库迁移机制（v1 → v2，带数据升级已测）；工作区层 8 个真实 git 集成测试；编排层 5 个端到端测试（用假 CLI，不消耗额度），覆盖隔离、检查点署名、追加消息继续同一任务、合并后开新任务、重叠文件提示、冲突阻止合并、中断保存进展、放弃保留分支、非 Git 目录报错。过程中测试抓出并修复了一个真实 bug：git 列出的是真实路径而本地路径可能经过符号链接，导致认不出已有 worktree。

已知限制：
- 项目没有 .gitignore 时，构建产物可能被当作改动提交；改动文件超过 5000 个会拒绝提交并提示检查 .gitignore。
- 任务分支不会自动跟进基础分支的新提交，依赖合并时的三方合并。
- 冲突目前只提示，尚不能让员工自动处理冲突。
- 界面尚未用真实 Claude 做过一次完整的"分配 → 检查点 → 合并"演练。

## 20.12 议题板与会议室（v0.2，已实现）

议题板：
- 议题（Issue）与任务、Bug 是不同对象。字段：标题、摘要、类型（技术方案/需求澄清/Bug 归因/风险/流程/代码细节）、高风险标记、提出人、负责人、候选方案、最终决定、决议原因、拍板人、取代关系。迁移 v4。
- 状态机在代码里强制：待讨论 → 讨论中 → 待决策 → 已决议 → 实施中 → 已关闭，另有搁置、已取消。不能绕过“拍板”直接变为已决议；已决议后不能退回讨论。
- 拍板权限在核心层强制并有测试：人类始终可以；需求类和高风险议题只能人类；一般技术方案由项目负责人；代码细节由议题负责人；没有 AI 负责人时 AI 不能拍板一般技术议题。
- 拍板时记录最终方案和原因，未采纳的方案保留并记录未采纳原因。已决议的议题不可修改；要推翻必须新建议题取代它，原记录完整保留。
- 待你裁决的议题出现在顶部 🔔 收件箱。

会议室：
- 会议 = 项目内的话题 + 类型（需求评审/方案评审/Code Review/QA Case 评审/复盘）+ 主持人 + 关联议题。
- 只有被 @ 的成员才被唤醒；没被点名的成员只旁听，不调用模型。被唤醒的成员各自并行，受全局并发上限约束。
- 会议发言走独立的只读会话（每个员工在每个项目一个，工作目录为项目根目录，不进入开发 worktree）。只读策略直接拒绝写入和非白名单命令，不弹审批，因此讨论不会改代码，也不污染开发会话。
- 省 token：员工首次发言带完整背景（会议、议题、方案、公司工程规范）；之后只带自上次发言以来的新消息和议题状态。消息数和字符数有上限，超出时丢弃更早的内容并注明。会议发言写入会议自身，不进入项目群聊事件流；成本事件带 meeting_id，便于以后统计。
- 每场会议有 AI 发言上限（默认 12），达到后 AI 不再发言，交由人类或负责人裁决。
- Code Review：可关联任务，评审人的提示包含该任务的 diff，并要求先独立判断；并发唤醒的评审人互相看不到对方的回复，天然保持独立。
- 纪要：由主持人（没有则负责人，再没有则第一位成员）一次调用起草，包含决议、被否方案及原因、行动项、待验证经验四节，人类可修改后保存。结束会议后不能再发言。
- 公司工程规范现已随会议首次发言注入（开发任务尚未注入）。

验证：核心层 49 个测试（含 3 个会议端到端：只读拒绝、上下文只发新增、发言上限、评审带 diff、纪要起草，均使用假 CLI，不消耗额度）；议题页、会议页已在真实界面渲染确认。

已知限制：
- AI 目前不能自己创建议题或拍板，这需要给它们结构化的工具接口，不靠解析聊天文本；权限规则已就绪，等接口接入。
- 纪要里的行动项不会自动变成任务，决议也不会自动更新议题，需要人工操作；纪要尚未自动写入项目记忆（记忆系统未实现）。
- 会议与议题的界面操作（新建、拍板、发言、起草纪要）尚未用真实 Claude 完整演练，仅逻辑层用假 CLI 验证。
- 站会见 §20.23，外部临时 AI 见 §20.22。

## 20.13 记忆系统（v0.2，已实现）

结构：公司、项目、员工个人、任务四层，统一存于 `memories` 表（迁移 v5），SQLite FTS5（trigram 分词，中英文都能匹配）。字段含来源、所属项目、创建时间、验证状态（待验证/已验证/已过期）、适用范围、相关提交、学习自哪条记忆、被注入次数。

核心规则（均有测试）：
- 防污染：人类手写的记忆直接为已验证；来自会议纪要等其他来源的一律“待验证”。检索只注入已验证的。待验证的候选可由人类验证或否决（删除）；已验证的不能删，只能标记过期，历史保留。
- 合并即验证（范围已收窄，见 20.19）：只有**显式关联到某任务**的待验证记忆，才会在该任务合并后自动转为已验证并记下合并提交；纪要里的经验和 AI 提议的记忆都不关联任务，必须人类验证。
- 议题决议自动沉淀为项目决策记忆（含原因和未采纳方案及原因）；新决议取代旧决议时，旧决议对应的记忆自动过期。
- 个人记忆独立：只有本人检索得到。员工只能学习“已验证”的项目/公司记忆，学习即复制为个人记忆并保留来源；不重复学习；个人记忆不能再被他人学习；不是项目成员不能学习该项目的记忆。
- 会议纪要“待验证的经验”一节由人类点击后存为待验证的项目记忆，不自动入库，重复保存不会产生重复条目。

检索与成本：
- 只在新任务开始时注入（继续同一任务不重复传递），会议则在员工首次发言时注入。
- 检索词来自任务描述：英文词（≥3 字符）和中文 3 字滑窗，加权命中分达到阈值才算相关；无关任务不注入任何内容。可见范围：公司记忆、本项目的项目记忆、本人的个人记忆、本任务的任务记忆。
- 上限：每次最多 6 条、约 1800 字，单条截断 450 字。
- 可测量：每次注入写入 `memory_injected` 事件（条数、字数、记忆 ID），每条记忆累计被注入次数；任务事件只记录原始任务描述，不重复存注入内容。
- 界面提供“检索预览”：输入任务描述，查看某员工会被注入哪些记忆。

界面：公司页“记忆”、项目页“记忆”、员工卡片“个人记忆”；待验证经验数量进入顶部收件箱；会议纪要区增加“把经验存入记忆”。

验证：核心层 60 个测试（记忆单元测试 8 个，端到端 3 个：新任务注入且只注入一次、无关任务不注入、合并后自动验证）。

已知限制：
- AI 目前不能自己写入记忆（需要结构化工具接口，不靠解析聊天文本），记忆只来自人工、会议纪要和议题决议。
- 检索是关键词匹配，不是语义检索；少于 3 个字符的中文词无法单独命中；向量检索留待后续。
- 任务层记忆目前只能通过会议纪要关联任务产生，尚未自动生成任务交接信息。
- 公司工程规范仍是独立字段，只在会议首次发言时注入。
- 记忆页的界面本轮只通过类型检查和后端测试，没有在真实窗口里看过渲染结果。

## 20.14 旧项目导入（v0.2，已实现）

流程：新建项目时勾选“这是已有的项目”→ 项目进入“导入中” → ① 只读扫描 → ② 测试基线 → ③ AI 联合评估 → ④ 人类确认 → 进入维护阶段。**导入中不能给员工派开发任务**（核心层强制，界面同步提示）；会议、议题等不受限。迁移 v6。

① 只读扫描（不调用 AI、不执行项目代码、不跟随符号链接）：
- 识别语言、包管理与构建工具、框架、数据库与中间件、测试框架、CI/CD（GitHub Actions、GitLab CI、Jenkins 等）、API 定义（OpenAPI/proto/GraphQL）、数据库 Schema 与迁移、README/CLAUDE.md 等文档。
- 模块结构：Cargo workspace、Maven 模块、npm workspaces、Go 模块；都没有声明时用含源码的顶层目录兜底。
- Git：分支、提交数、标签、首次提交日期、最近提交、主要贡献者、远程地址（自动去掉其中的凭据）、是否有未提交改动。
- 支持 Rust、Node（npm/pnpm/yarn）、Maven、Gradle、Go、Python 的构建/测试命令建议。
- 扫描很快，“项目地图增量更新”目前用重新扫描代替；基于 AI 的调用链、业务流程分析尚未做。

② 测试基线：
- 扫描只“建议”命令，由人类勾选、可编辑、可追加，并在运行前明确确认——因为构建和测试会执行项目里的代码。
- 命令在已提交 HEAD 的**干净检出**里运行（数据目录下的临时 worktree，运行后清理）：不改动用户的工作目录，构建产物不会出现在用户的目录里；未提交的改动不包含在基线内（界面会提示）。依赖安装失败时，其余命令标记为跳过。
- 记录每条命令的原始结果：状态、退出码、耗时、输出末尾；从输出中解析出逐项失败的测试（cargo、pytest、go、Maven、Gradle、jest/vitest）。解析不了就明确标记，不假装能区分。

来源判定（对比基线与当前结果，逐项）：
- 导入前就失败、现在仍失败 → 导入前已存在；基线通过、现在失败 → AI 引入；基线失败、现在通过 → 已修复；
- 两边都失败但无法逐项比较（如编译错误、没有解析器）、基线没跑过该命令、基线里被跳过 → **无法确认来源**，不归咎于任何一方。
- 任务面板的“对比基线检查”：先保存员工的未提交改动，再在任务分支的干净检出里运行基线同样的命令并判定，结果持久化；员工的 worktree 不被构建产物污染。

③ AI 联合评估：全栈（架构、模块地图、技术债、建议开发计划）与 QA（测试覆盖与缺失的回归测试、潜在缺陷、兼容性、安全风险、风险清单）各出一份只读报告；提示里带扫描结果和基线，并明确告知基线里已有的失败是历史问题，不得归咎于后续修改。

④ 人类确认：没有基线不能确认，除非明确选择跳过（跳过会被记录）。确认后把“技术栈与项目结构”“导入时的测试基线”（明确写出哪些失败是导入前就存在的）存为已验证的项目记忆，项目转入维护阶段。

验证：扫描器 6 个、基线与判定 5 个单元测试，导入端到端 6 个（真实 git 仓库 + 假命令：干净检出不碰工作目录、导入阶段闸门、确认规则、历史失败与 AI 引入的区分、评估提示内容）；另有默认忽略的冒烟测试，在本仓库上跑真实 `cargo test` 基线并成功解析。命令行新增 `crewforge scan`，已在本仓库上验证。导入页已在真实窗口渲染确认。

已知限制：
- 安全扫描未做（需要依赖外部工具与网络，暂不内置）；基线只覆盖构建、测试、lint 类命令。
- 基线在干净检出里从头构建，没有缓存，大项目首次会比较慢（默认单条命令超时 15 分钟）。
- 逐项解析只覆盖上述几种输出格式；其他测试工具只能做命令级对比。
- 评估报告目前存在数据库里，没有自动写入项目仓库的 docs/；评估是一次性的，没有增量更新。
- 只在 macOS 上验证过；命令通过 `sh -c` 运行，Windows 支持留待以后。
- 导入页的完整操作（运行基线、请求评估、确认）没有用真实 Claude 和真实用户项目完整演练，评估部分只用假 CLI 验证。

## 20.15 成本与额度统计（v0.2，已实现）

数据来源：全部来自事件流里每轮调用的真实记录，没有另建一套统计。为了能按项目、用途拆分，本次给 `turn_result` 事件补充了用途（开发任务/会议发言/纪要起草/导入评估）、归属项目和耗时；会议与评估的事件本身不在项目群聊里显示，但成本照样算到项目头上。旧事件没有这些字段，统计时通过任务或会议反查归属，查不到的单独列为“未归属项目”。额度事件补充了窗口重置时间。

口径（界面和代码里都明确写出）：
- 费用是 CLI 报告的等值估算，**不是订阅账单上的实际扣费**。
- CLI 没给出的数据标“未知”，不按 0 计入，不估算；各汇总里单独统计“有数据的轮数”，平均值只按有数据的轮数算。
- `input_tokens` 只是未命中缓存的输入；“处理的上下文 token”= 未缓存输入 + 缓存读 + 缓存写，另列输出 token。

页面内容：订阅额度（5 小时/7 天使用率、重置倒计时、走势、85% 警戒线）；调用次数、估算费用、上下文 token、输出 token、平均耗时；每日用量柱状图（费用或 token）；按员工、按项目、按用途的汇总表；花费最多的任务；时间范围（今天/7 天/30 天/全部），按本地时区按天归并。

可测量的省 token 指标：平均每轮上下文、缓存命中率、会话复用率（开始执行时接续已有会话的比例）、每任务平均轮数、记忆注入次数及平均条数/字数、会议里人类发言与 AI 回复的数量、执行失败与会话恢复次数。

验证：5 个单元测试（新旧事件格式的归属、未知数据不计为 0、按天与时区归并含闰日、效率指标、额度序列降采样）；命令行 `crewforge cost` 在真实调用产生的数据上与直接查库逐项核对一致；成本页已用真实数据在窗口里渲染确认。

已知限制：
- 目前只有一个执行引擎和一个账号，没有按账号/引擎拆分。
- 重试次数尚未单独统计（尚无自动重试机制）。
- 额度使用率来自最近一次调用的返回，不是实时的，也无法把额度消耗精确归因到某个员工；只能用各自的估算费用占比参考。
- 旧事件缺少耗时、用途、重置时间，对应位置显示“未知”。
- 没有预算/告警功能（只有界面上的 85% 警戒线）；调度器尚未据额度自动降速。

## 20.16 AI 员工自己提议题与经验（v0.2，已实现）

做法：通过 MCP（Claude Code 官方的工具扩展协议）给员工提供结构化工具，不靠解析聊天文本。MCP 服务器就是 Crewforge 自己的可执行文件的 `mcp-serve` 子命令（命令行和桌面应用都支持），由 Claude Code 按 `--mcp-config` 启动。启动参数里写死员工、项目和来源（`task:<id>` / `meeting:<id>`），员工无法冒用别人的身份；每次调用都重新校验“是项目成员且未归档”。它与应用共用同一个 SQLite 库（跨进程写入，WAL + 忙等待）。

工具（AI 只能提议，**没有拍板工具**）：
- `list_issues`：列出未结束的议题和近期决议，提议前先查重。
- `propose_issue`：提议议题（可带最多 4 个候选方案）。议题进入“待讨论”，等人类确认后才开始讨论；人类可“接受，开始讨论”或“驳回提议”。
- `add_option`：给还没有结论的议题补充候选方案。
- `request_decision`：把“讨论中”的议题推进到“待决策”，进入有权限者的待办；“待讨论”的议题不能直接请求拍板。
- `propose_memory`：提议经验，进入“待验证”，验证前不会注入任何员工。只能是项目级或本人个人级，**公司级记忆不对 AI 开放**；不关联任务，因此不会因任务合并而被自动验证（AI 的断言不是合并能证明的）。

防滥用（均有测试）：标题 ≤ 80 字、摘要 ≤ 600 字、记忆 ≤ 600 字；每次任务/会议最多提 3 个议题、3 条记忆；每名员工在一个项目里同时未处理的议题 ≤ 5、待验证记忆 ≤ 5；查重——议题标题与未取消的议题做字符二元组相似度比较（≥ 0.7 视为重复，拒绝并指向已有议题，提示改用 `add_option`），换个说法也能识别；候选方案同理；记忆内容完全相同则拒绝。拒绝的原因作为工具结果返回，模型看得到并能调整。

权限：团队协作工具由策略自动放行（只写“提议”，不改代码），只读的会议会话里同样可用；其他 MCP 工具照常需要审批（只读模式下直接拒绝）。

界面：AI 的提议在项目群里显示（💡提议议题 / ➕补充方案 / 🗳请求拍板 / 🧠提议经验），议题板标出“XX 提议”和“等你确认是否讨论”，顶部收件箱列出待确认的 AI 提议。事件由应用定时读取事件表推送给界面（MCP 服务器和命令行是别的进程，进程内钩子收不到它们的事件）。

重要修正（影响所有员工进程）：实测 `--safe-mode` 会把 `--mcp-config` 一起关掉。员工进程改用 `--setting-sources ""`（不加载任何设置来源）+ `--disable-slash-commands` + `--strict-mcp-config`，并总是传 `--mcp-config`（没有协作工具时传空，屏蔽用户自己的 MCP）。已实测：hooks 0 个、技能 0 个、你安装的 Postman 插件不加载、项目里的 CLAUDE.md 同样不加载（与之前的隔离效果等价），登录不受影响。

验证：MCP 服务器 9 个单元测试（协议、身份、状态机、查重、两种限流、记忆）；真实 `crewforge mcp-serve` 进程 4 个测试（stdio JSON-RPC、stdout 只含协议消息、身份来自启动参数、两个服务器进程加应用进程并发写库不报 database is locked）；默认忽略的冒烟测试用**真实的 Claude** 跑通：它启动我们的 MCP 服务器，按顺序调用 list_issues、propose_issue、propose_memory，全程没有触发人类审批，议题和记忆正确落库并带来源（约 $0.07）。

已知限制：
- AI 仍不能自己拍板；让有权限的 AI 负责人在技术类议题上拍板，需要另行设计（权限规则已在核心层，待接入工具和确认机制）。
- 团队协作工具只提供给开发任务和会议发言；导入评估和纪要起草没有提供。
- 身份靠启动参数约束；员工若能绕过策略直接执行系统命令，理论上可以自己启动 mcp-serve 冒用身份，目前由“非白名单命令需要审批”挡住。
- 查重是字符相似度，不是语义比较，措辞差异很大的重复议题仍可能漏掉，由人类在确认环节把关。
- 提议次数的限流是软限制（按事件计数），没有做成严格的事务级配额。
- 本轮没有在真实窗口里重新查看议题板和收件箱的新增显示，只通过了类型检查。

## 20.17 额度感知的调度（v0.2，已实现）

背景：所有员工共享同一份订阅额度，原来只有固定的并发上限，完全不看额度。现在所有模型调用（开发任务、会议发言、纪要起草、导入评估）都先经过调度器取得许可。迁移 v7 新增 `settings` 表，保存并发上限和调度配置（重启后保留）。

分级策略（按最紧张的那个窗口，5 小时 / 7 天）：
- 低于限速线（默认 70%）：正常，按设置的并发上限。
- 达到限速线：并发减半（向上取整，至少 1）。
- 达到严格限速线（默认 85%）：并发降为 1。
- 达到暂停线（默认 95%），或 CLI 明确报告被限流：暂停新任务，等窗口重置后自动恢复；两个窗口都拦路时取较晚的恢复时间。
- 阈值可调（需满足 0 < 限速线 < 严格限速线 < 暂停线 ≤ 100%），可整体关闭调度。

读数过期的处理：额度读数只在有调用时才更新，所以不能永远卡住。已知的重置时间到了就当该窗口已重置；不知道何时重置的暂停，读数超过 30 分钟后先放行 1 个任务去确认当前额度，而不是一直暂停。

排队：先来先服务；等待中的任务被取消时从队列里摘掉，不占位；新的额度读数到来、设置变化、任务结束都会唤醒排队者重新评估，另有每 5 秒的定时复查（所以窗口到期会自动恢复）。
- 开发任务：不能立刻开始就排队，并记录排队原因（并发已满，或具体的额度原因），群里显示。
- 交互式操作（会议发言、纪要起草、导入评估）：暂停时直接提示原因，不排队——避免一条回复几个小时后才冒出来；只是限速时照常排队。

用户控制：手动暂停新任务；“忽略额度限制 30 分钟”（临时，不改阈值；手动暂停优先于它）；调整阈值与开关。顶部栏在非正常状态下显示状态条（暂停/限速/排队数、预计恢复时间，并提供“仍然继续 30 分钟”或“取消暂停”）；设置页显示当前状态、有效并发、原因，并提供配置。调度状态变化时写入 `scheduler_state` 事件，界面据此更新，并每 15 秒定时刷新。

命令行 `run` 也走同一个调度器、读同一份额度数据（与应用跨进程共享读数）；`--max` 只对当次生效，不写入设置。

验证：11 个调度器单元测试（分级边界、窗口重置、读数过期探测、限流状态、先来先服务、取消的排队不占位、读数更新后立即放行、窗口重置后无需外部通知自动恢复、手动暂停与临时忽略的优先级、交互式拒绝、状态变化只发布一次，异步部分用虚拟时间）；命令行真实运行验证：额度 97% 时 `crewforge run` 输出“排队中：5 小时窗口已用 97%，超过暂停线 95%”且没有产生任何任务或模型调用，额度降到 30% 后立即越过排队开始任务。

已知限制：
- 调度只能控制“新任务何时开始”，不会中断已经在运行的任务。
- 额度使用率来自最近一次调用，不是实时的；多个任务同时开始时，在第一个读数返回之前，调度器看到的还是旧数字。
- 只有一个账号；多账号时需要按账号分别调度。
- 并发与额度状态只在一个应用进程内统计“运行中”的数量，应用和命令行同时跑时互相看不到对方占用的名额（额度读数是共享的）。
- 排队中的任务在应用退出后会丢失（不会自动恢复）。
- 本轮没有在真实窗口里查看状态条和设置页的渲染，只通过了类型检查。

## 20.18 完整真实演练（v0.2）

做法：用**真实的 Claude** 跑完整条链路，演练脚本是默认忽略的测试 `crates/cli/tests/walkthrough.rs`（`WALK_DIR=某目录 cargo test -p crewforge-cli --test walkthrough -- --ignored --nocapture`），可以重跑。项目是临时造的小 Rust 账户库（`withdraw` 允许透支，对应测试在导入前就失败），数据目录隔离，不碰用户的数据和代码。

流程与结果（共 42 项检查，全部通过；约 2 分钟、7 次模型调用、估算费用约 $0.43，演练结束时 5 小时窗口 59%、7 天窗口 8%，调度器未暂停）：
1. 导入：导入阶段不能派任务；扫描识别 Rust 与 Git 历史；真实 `cargo` 基线在干净检出里运行，解析出导入前就失败的 `withdraw_rejects_overdraft`，用户目录未被弄脏；全栈与 QA 两份评估都给出结构化报告并如实提到透支问题；确认后沉淀 2 条已验证记忆。
2. 开发：alice 实现 `transfer`，改动只在她自己的 worktree，主工作区不动，检查点以 alice 署名。
3. 对比基线：历史遗留的透支测试被判为“导入前已存在”，没有归咎于 AI；bob 的第二个任务同样。
4. 评审会议：bob 只读评审，发现了真实的整数溢出问题；bob 通过 MCP 工具自己提议了议题；alice 回应；主持人起草了结构化纪要；纪要里的经验存为待验证记忆。
5. 议题：AI 提议的议题进入“待讨论”，人类确认、拍板后自动沉淀为已验证的决策记忆。
6. 合并：两个任务都 squash 合并成功（第二个基于合并后的新基础，无冲突）；关联任务的经验合并后自动验证；主分支历史由 alice、bob 署名并带任务编号等追溯信息。
7. 记忆：第二个任务开始时注入 4 条相关记忆（671 字），bob 遵守了“金额用 i64、不用浮点或 Decimal”的约定。
8. 成本：7 次调用与事件一致，全部归属到项目；按用途、员工拆分正确；缓存命中 87%。

演练暴露的问题（42 项检查没有覆盖，是翻原始记录发现的）：
- **评审与合并是断开的（已部分修复）**：bob 在评审里指出溢出问题、alice 当场同意修，但合并时没有任何提醒，这个 bug 随着合并进了主分支。现在任务卡显示关联的评审会议（进行中/已结束、行动项数量），合并确认框会列出未结束的评审和纪要里的全部行动项。真实纪要有 6 条行动项，合并时全都还没处理，新逻辑会把它们摆出来。**仍然只是提醒，没有强制拦截**，也不会把行动项自动变成任务。
- **审批卡片对多行命令几乎不可读（已修复）**：员工用 `python3 - <<EOF` 改文件时，原来把命令当 JSON 字符串显示，换行变成转义。现在 Bash 命令按原样显示（保留换行），文件写入显示路径与内容。
- **从纪要提取经验时把“无。会上没有新增……”当成了一条经验（已修复）**：纪要的“待验证的经验”一节写着“无”后面跟一句解释，旧的提取逻辑只认整行等于“无”，把整句话存成了待验证记忆，随后又因任务合并被自动验证，成了一条已验证的垃圾记忆。这是读完整纪要才发现的——演练里“存入 1 条”的检查通过了，却没有核对内容。现在识别“无/暂无/没有”后紧跟标点、以及“没有新增/无需/不涉及”等固定说法，并去掉 Markdown 加粗标记再判断；“无法连接 Redis 时…”“没有索引时…”这类正常句子不受影响。演练脚本新增了“存进记忆的内容必须是真正的经验”的检查。另外脚本里选错了议题选项，导致决策记忆自相矛盾，也一并修正（那是脚本的问题，不是产品的）。
- **CLI 自己会放行它认为“只读”的命令**：如 `git ls-files && cat … | head`、`cat src/*.rs; ls` 这类组合，根本不经过我们的审批层，所以我们的策略不是唯一的闸门。写入、改文件的命令都会到我们这里，演练中评审是只读的这一点得到验证，但这个边界取决于 CLI 对“只读”的判断。
- **员工常用 Bash 的 python 脚本改文件，因此每个任务会遇到 1~3 次审批**：任意 Bash 能做的事太多，无法安全地自动放行，这是预期行为；真正的解决办法是给员工进程加沙箱（如 macOS sandbox-exec），尚未做。
- 小问题：员工通过 ToolSearch 先加载 MCP 工具再调用，多一轮；库项目里员工生成的 `Cargo.lock` 被检查点提交进了仓库（不是 Crewforge 的问题，取决于项目的 .gitignore）。

没有覆盖到的（演练走的是核心层和命令行路径，也就是界面背后实际调用的那一层）：
- **桌面界面本身**：点击流程、各页面渲染、审批卡片的交互、排队与调度状态条的实际显示。
- Tauri 命令这一薄层（成员与导入阶段的校验在核心层，已覆盖；命令封装本身没有端到端测试）。
- 崩溃恢复、多员工同时排队的真实场景、Windows。
- 只演练了一个很小的项目；大项目的基线耗时、扫描规模、上下文长度的影响没有验证。

## 20.19 评审行动项与合并的关联（v0.2，已实现）

背景：第一次真实演练里，评审发现了溢出 bug，但合并时没有任何拦截，bug 随合并进了主分支。

- 纪要保存时（自动起草和手动修改走同一条路）自动把“行动项”一节同步成可跟踪的记录（迁移 v8）：负责人、状态（待处理/处理中/已处理/已驳回/已撤回）、是否阻塞合并。重复保存不产生重复；改纪要不丢已有状态；从纪要里删掉且还没处理的标为“已撤回”，已处理的不动。
- 纪要提示词要求每条写成「- [合并前] 负责人：事项」或「- [之后] 负责人：事项」。`[合并前]`（以及没写标签的，宁可多问）会拦住**被评审的那个任务**的合并；没有评审对象的会议里的行动项永远不拦合并。
- 合并门：有未处理（待处理或处理中）的合并前行动项时，合并默认被拦下并列出这些条目；人类可以明确选择“仍然合并”，会留下 `merged_with_open_items` 记录。命令行 `crewforge merge <id> --ack` 同理。
- 只有人类能把行动项标为已处理、驳回（必须写原因）或重新打开；AI 员工没有这个权限。员工改完只是“处理中”，仍拦合并，要人确认。
- 行动项可以直接派给员工处理（提示里带条目和会议名）。对进行中任务的评审意见只能交给该任务的员工，在同一个任务、同一个分支里继续修，否则修复会落在别处、被评审的代码并没有变；任务合并后遗留的后续事项可以交给别人另开任务跟进。
- 界面：会议页的行动项面板（派活、已处理、驳回、重新打开），任务卡显示评审与未处理的合并前行动项数，合并被拦时的明确确认框，收件箱提示未处理的行动项，群里显示相关事件。

第二次真实演练（58 项检查全部通过）：模型按要求打了标签并解析出负责人；合并被拦下；派给 alice 后她在同一个任务里用 `checked_add` 修好了溢出，没有引入新失败；员工改完仍拦合并，人确认后才合并；这回主分支上没有带着 bug。

这次演练又读出两个问题（检查全绿没有抓到）：
- 纪要“待验证的经验”里写的是“新增测试是否通过，目前没有运行结果”“基线失败仍然存在，要等…”这类**当时的状态**，不是经验；它们因“合并即验证”被自动验证成已验证记忆，而前一条合并后其实是错的。合并能证明代码通过了评审和测试，证明不了模型写的这句话。**已修复**：纪要里的经验不再关联任务，必须人类验证；纪要提示词也明确“经验”只写以后能复用的做法或教训，当前状态、未解决的问题、待办不是经验。
- 纪要里 5 条“合并前”只有 1 条是真正的代码修复，其余是“运行测试确认通过”“确认 amount==0 是否合法”这类验证步骤或人类决定。**已收紧提示词**：只有不解决就不该合并的缺陷或必须补的测试才标合并前，例行验证不列为行动项，需要人类拍板但不影响正确性的写成之后。
- 演练脚本往 AI 提议的议题里塞了无关选项、选错方案，造出了假的决策记忆（脚本问题，已修）。

### 20.22 外部临时 AI（Guest / 外部顾问）

- 用户在会议里点“邀请外部顾问”，填名字和“请他回答什么”，直接生效（用户自己邀请视为已批准；成员或系统发起的邀请仍应先取得人类批准，由调用方负责）。
- 实现：顾问是 role=`guest` 的临时员工记录 + `meeting_guests` 表（目的、邀请人、过期时间，默认 24 小时、最长 72 小时）。不进公司花名册（`list_employees` 过滤），不是项目成员，只属于邀请他的那场会议。
- 最小上下文：全新会话；提示只含邀请目的、本会议的议题、讨论；不带公司规范、项目记忆、其他会议。只读（沿用会议只读策略），没有团队协作工具（不能提议题或记忆），无权拍板。会议结束（`close_meeting`）时自动归档离场，到期或手动“请离场”后不能再被唤醒；发言和会话保留以便追溯。
- 被 @ 的名字同时匹配成员与在场顾问，发言计入本场 AI 发言上限与额度调度。
- 验证：集成测试（名字/目的/重名校验、不在花名册、提示里有目的与议题而没有公司规范和 `propose_*`、写文件被拒、会议结束后离场、不能进入别的会议）；真实 Claude 冒烟（`crates/cli/tests/real_guest.rs`）：顾问读 `store.py` 给出非原子写入风险的结论，要求它创建文件被拒。
- 未做：来源选择（目前只有 Claude 全新会话；Copilot 等其他 Provider 需账号）、成员主动请求引入的审批流、顾问结论“采纳/否决”自动写入项目决策（现在由人在议题里决定）。

### 20.23 站会（同步进度、对齐理解）

- 定位：站会是会议类型 `standup`，复用会议室、纪要和行动项，不引入新机制。目的是让并行工作的工程师同步进度、对齐接口与先后顺序的理解，防止对接混乱；**不做决策**，发现的不对齐点变成行动项，由人和负责人会后决定。
- 流程：① 系统从数据库汇总每个成员的事实（进行中的任务、分支、已改动的文件、计划条目及等待项、未处理的评审行动项），不调用模型；有进行中任务或计划条目的成员才参会，没有人在做事则不开。② 参会成员按固定顺序各发言一次，格式固定为“做完了 / 在做 / 被卡住 / 依赖别人（含对接假设）”，后发言者能看到前面的报告，以系统记录的现状为准。③ 系统做一次确定性的对齐检查：多人改了同一个文件、依赖未完成的条目、被阻塞的条目、拦合并的评审行动项。④ 主持人起草纪要（站会模板：进度同步 / 不对齐点 / 行动项）。
- 成本：每位参会成员一次调用 + 一次纪要，三人团队约 $1。正在执行任务的成员不被打断，以系统记录为准。
- 界面：会议页“站会”按钮；有两个以上成员并行做任务时给出提示。手动触发，不做定时。
- 验证：集成测试（没人做事时不开会、只有在做事的人参会、事实里有任务和文件、提示是站会格式、后发言者看得到前面的报告、同文件被两人修改被发现）；真实 Claude 冒烟（`crates/cli/tests/real_standup.rs`）：两人任务描述里字段分别是 `userId` 与 `user_id` 且改了同一个 `api.md`，双方发言都指出了字段不一致、文件归属不明和先后顺序没人确认，纪要生成 4 条行动项。
- 已知局限：站会没有关联任务，所以纪要里的 `[合并前]` 不会拦任何合并（只是标记优先级）；“多人改同一文件”只比对文件路径，不识别同一接口的不同文件。

### 20.24 沟通规范（让 AI 之间一次就读懂）

- 动机：AI 之间说话没头没尾、没有量化，接收方只能追问确认，浪费时间和 token。做法是在下游最容易误读的节点加一小段输出规范（具体 / 可量化 / 有依据 / 可执行 / 有边界），不增加调用。
- 节点：① 所有任务与会议：系统提示里追加通用规范；② 任务完成汇报：固定四行（做了什么 / 验证（命令+数字）/ 没做或已知问题 / 需要别人配合）；③ 站会发言：四项都要带对象和数字，依赖要写明对方的什么产物及假设；④ 评审意见：先给总体结论，每条「【拦合并/建议】文件:位置 — 问题 — 期望改法」，最多 8 条；⑤ 纪要行动项：「负责人：做什么（对象，完成标准）」。
- 检查：任务汇报做一次不调用模型的检查（没有数字、没说怎么验证、超过 1500 字），写入 `report_flags` 事件，只提醒不拦流程。设置项 `protocol=off` 可整体关闭。
- 效果对比（真实 Claude，同一场景开/关各跑一次，样本很小，只能看出格式上的差异）：行动项带“完成标准”：关 0/4 → 开 3/3；任务汇报带验证命令与通过数（如“2/2”）：关为叙述性文字、没有计数 → 开是四行且有计数；站会发言字数 557 → 716（+28%）、汇报 239 → 306 字；总输出 token 2560 → 2506、费用 $0.144 → $0.131，基本持平。
- 没有证明的事：“省掉追问”。这个对比只证明输出更具体，没有度量下游 AI 因此少问了多少。要验证需要让接收方（如 bob 读 alice 的汇报）去执行，统计追问或返工次数。

### 20.25 用量统计增强（参考 CC Switch 的用量功能）

- 参考对象：本机 CC Switch 的用量页与数据模型（请求日志表含模型、四类 token、拆分成本、耗时与首字时间；按天汇总；模型价格表）。只看了表结构，没有读取其中的账号数据。

### 20.26 Copilot CLI 适配

- 员工可以选执行引擎：`claude`（默认）或 `copilot`（创建时选，不可改；命令行 `crewforge employee add 名 岗位 说明 --provider copilot`，界面“新员工”里有下拉）。运行器按员工的引擎启动对应进程，两者给出同一种事件流，上层（任务、会议、检查点、成本）不关心是谁。
- 调用方式：`copilot -p <提示> --output-format json --session-id <我们的会话 id>`，每行一个 JSON 事件（`assistant.message`、`tool.execution_*`、`session.usage_checkpoint`、`result`）。会话 id 复用，所以追加消息接续同一会话；角色设定放在新会话第一条消息开头（没有单独的系统提示参数）；`--no-custom-instructions` 避免用户或仓库的指令文件干扰；`--disable-builtin-mcps` 关闭内置的 GitHub MCP。
- **权限与 Claude 不同**：Copilot 非交互模式没有“边跑边问人”的通道，所以权限在启动时一次定好：开发任务允许写入（路径校验只放行工作区与临时目录，不放宽）与一份开发命令清单（git add/commit/status/diff…、cargo、npm、python3、go、make 等）；`git push`、`sudo`、`ssh`、`curl`、`wget`、`rm` 等永远拒绝（拒绝优先于一切允许）；清单之外的命令被直接拒绝，模型能看到原因并改用别的办法。因此 Copilot 员工不会产生审批请求，也不能删除文件。会议里是只读：拒绝所有写入，只允许 ls/cat/grep/git diff 等查看命令。不使用任何 `allow-all`。
- 团队协作工具：同一个 `crewforge mcp-serve`，通过 `--additional-mcp-config` 提供并放行。
- 用量：Copilot 按“高级请求”和 AIU 计量，没有 token 与美元费用——这些记为“未知”，不会当成 0。成本页新增“Copilot 高级请求”卡片，按模型分组时标注“（Copilot）”，调用明细里费用列显示“n 高级请求”。Copilot 没有 5 小时/7 天额度读数，调度器的额度分级对它不起作用（并发上限仍然有效）。
- 验证：解析器与参数的单元测试（含真实输出样例）、假 Copilot 的端到端测试（权限参数、会话复用、不重复角色设定、无审批请求、用量口径）、真实 Copilot 冒烟（`crates/cli/tests/real_copilot.rs`，约 3 次高级请求）：任务在员工 worktree 里创建了文件、主工作区未被改动，`git push` 被规则拒绝，会议里调用了 `crewforge` 的 `list_issues`；只读规则单独用真实 CLI 验证：`--deny-tool=write` 下创建文件返回 denied。
- 已知局限：不能在运行中向人请求权限（要用某个清单之外的命令只能先改清单）；没有 Copilot 的额度读数，无法按额度调度；沙箱（Copilot 自带的命令沙箱）没有启用；模型选择用 Copilot 的默认值。

### 20.27 员工的执行引擎与模型可编辑

- 编辑员工时可以改执行引擎和模型（之前引擎创建后锁定，模型无法选择）。模型留空 = 引擎默认；非空时传给 CLI 的 `--model`（Claude 可用别名 sonnet / opus / haiku；Copilot 用其模型 id）。只改模型不影响会话；切换引擎会清掉该员工的会话（两个引擎的会话不通用，之前的对话上下文不带过去），任务分支、工作区、历史事件、记忆都保留；员工正在执行任务时不能切换引擎。
- 验证：单元测试（只改模型会话保留、切换引擎会话重置、非法引擎与带空格的模型名被拒绝、参数里只在设置了模型时才有 `--model`）；真实 Claude：`--model haiku` 实际使用 `claude-haiku-5-5`；真实 Copilot：写错模型名时 CLI 以退出码 1 并在 stderr 报 “Model … is not available”，运行器会把这段原文带进错误信息。

### 20.28 引擎与模型管理、用量页改版

- **引擎激活**：Claude Code、GitHub Copilot 各有“激活”开关（默认激活）。停用后不能新建员工或切换到它；用它的员工执行时被拒绝并提示原因（不启动进程）。页面显示是否检测到可执行文件、版本、路径；Copilot 可改路径，或“安装到应用目录”（npm 装到数据目录的 `tools/`，不动系统全局）。
- **模型清单**：每个引擎一份可选模型表（`models` 表）。Claude 内置 opus / sonnet / haiku 别名和完整模型名；Copilot 可“发现模型”——读取 `copilot help config` 里列出的模型（含 Claude、GPT、Gemini、Grok、Kimi 等），也可手动添加任意模型名。内置或发现的只能停用，自己添加的可删除。用户的启停不会被再次播种覆盖。
- **选模型的优先级**：员工自己指定的模型 > 该引擎在这个用途下的默认模型 > 引擎默认。用途分开发任务、会议发言、纪要起草、导入评估，所以可以“开发任务用 Opus，会议和纪要用 Haiku；Copilot 的开发任务用 Grok”。
- **用量页**（原“成本”）改成左右布局：左侧是章节（概览、额度、按引擎、按模型、按员工、按项目、按用途、调用明细、花费最多的任务、省 token 效率）和时间范围，右侧是内容；新增“按引擎”维度和调用明细的引擎过滤；额度一节说明 Copilot 没有额度读数只按高级请求计数。“模型”页同样是左右布局（左：引擎和“按用途的默认模型”，右：详情）。
- 顺手修复：项目成员排序在同一毫秒加入时不稳定（站会发言顺序依赖它），现在加上名字作为第二排序键。
- 没做：整个应用的导航（顶部公司/项目标签和项目内的子标签）仍是顶部布局，只有用量页和模型页是左右布局。

### 20.30 用量页按 CC Switch 的结构重做

- 参照对象：CC Switch 开源仓库里的用量组件（`src/components/usage/*`）。照它的页面结构和功能做，数据和口径换成我们自己的（员工、项目、用途、引擎、模型）。
- 页面结构：页头（标题、更新时间、刷新、设置）→ 时间范围条（今天 / 24 小时 / 7 / 14 / 30 天 / 全部 / 自定义日期）→ 筛选条（引擎切换按钮，按钮上带请求数；员工、模型、项目、用途、状态下拉；清除筛选）→ **概览面板**：一排可点的指标格（总请求数、估算费用、真实总 Token、新输入、输出、缓存读/写、缓存命中率、成功率、耗时中位/P95 与首字平均、输出速度、Copilot 高级请求），选中的指标决定下方图表画什么；图表在范围不超过 48 小时时按小时、否则按天，Token 图按四类堆叠并带悬停提示；选“全部”时改画最近一年的热力图 → **页签**：请求明细 / 模型 / 员工 / 项目 / 用途 / 效率与额度，页签上带数量。
- 请求明细：可选的列（时间、引擎、员工、用途/内容、模型、费用、新输入、输出、缓存读、缓存写、命中率、速度、首字、耗时、状态；选择会记住）、每页条数、分页；点一行打开右侧详情（基本信息、Token 构成、费用与按模型的拆分、性能、错误）。各统计表有请求数、Token 各类、命中率、费用、平均费用/次、成功率。
- 后端新增 `usage_overview` / `usage_stats` / `usage_calls`：同一套筛选条件（起止时间、引擎、员工、项目、模型、用途、状态）；各筛选菜单的选项不受自己那一维筛选的影响；一次用了多个模型的调用，在“按模型”里按各模型自己的用量拆开；缺失的数据是“未知”，不当成 0。
- 与 CC Switch 的差异：没有价格表（费用直接用 CLI 的估算）；没有“解析本机会话日志补充数据”；额度与省 token 效率放在最后一个页签里。

### 20.31 “我的职责”：让人类知道自己在系统里是谁、该管什么

- 起因：用户在处理待办时对自己在项目里的定位感不强。根因有三：系统里没有“我”的页面；待办只列清单、不说为什么轮到人；还有大量“不该是人的待办”（演练遗留的 47 条评审行动项）把真正需要人的事淹没。
- 身份定义（来自 20.4 与 20.6，原先只在文档里）：人类是项目负责人（CTO / 架构师）。只有人能决定：需求与业务方向、涉及资金/生产/不可逆/安全的事、确认 AI 起草的计划、里程碑验收。需要人把关：合并到主分支、关闭评审行动项、验证 AI 总结的经验、越权操作的审批。不需要人管：写代码、跑测试、互相评审、起草计划与纪要、提议题和经验、处理评审意见。AI 能提议，没有拍板工具。
- 项目里新增第一个页签“职责”：身份说明；“现在在等你”清单，每一项带类型、为什么是你、一键去处理；“只有你能决定 / 需要你把关 / 不需要你管”三栏；另列“之后再说”的行动项数量。
- 待办收件箱：每一条都标注类型和“为什么是你”；评审行动项只统计真正轮到人的两类——拦着合并的（员工改完后要人确认）和评审里指明给人的；“之后”类、给 AI 的小事不再进收件箱，只留在会议页。真实数据上：待办从 47 条变成 5 条（贪吃蛇 2、ledger 3），都是真问题（NaN 排序是否复刻、棋盘填满是否区分胜负、回车重开是否还要再按方向键等）。
- 命令行：`crewforge duties` 列出每个项目里等你的事和原因。
- 没做：公司层面的“我的职责”；让用户自己调整想承担的范围（现在是固定定义，要改先改文档里的定义）。

### 20.32 自主推进：讨论定稿后由负责人主导，人旁观和纠偏

- 方向（用户定的）：人类必须做的是创建项目、设置、配置员工，以及新项目和导入项目阶段的讨论分析；讨论定稿后，后续所有任务由项目负责人主导并主动发起，人类是旁观者和纠偏者（在群聊里协助 AI 纠偏）；负责人管理群聊、计划、任务、议题、会议、记忆、文档；如果负责人是人，就由人担起这些职责。
- 边界（用户选的）：负责人只在 **预算用尽、反复失败、需求类或高风险议题等人拍板、人手动暂停或停止** 时停下；技术方案、合并、评审意见、行动项、站会都由负责人自己定。运行方式是 **按“预算批次”**：开始时设最多多少次调用、多少分钟，用完自动暂停并汇报，人看过再开下一批。
- 实现（`autopilot.rs`，把之前手写的演练驱动变成产品功能）：项目要有 AI 负责人；点“开始”就是对计划的最后确认（提议中的计划条目一并批准）；一圈流程——按依赖并行派计划条目 → 验证（有基线就对比基线，失败让负责的员工修，最多 3 次）→ 评审会议由负责人主持，纪要起草 → 行动项：拦合并的交给任务负责人修，指明给人的或不属于该任务负责人的写明原因留到之后（不进人的待办）→ 合并（冲突交给任务负责人解决）→ 第一个任务合并后建立测试基线；有两个以上任务并行时开站会（限流：之后至少合并过一个任务才再开）。忙碌的员工（含人正在驱动的）不派活，派出去的登记为“工作中”。暂停：手上的做完就停；停止：做完当前一步就停。应用重启时，上次“推进中”的批次标为已停止。
- 界面：项目的“职责”页顶部是“自主推进”面板——状态、本批次已用调用数与预算、开始（设预算）/ 暂停 / 停止、负责人动态时间线（派活、验证、评审、合并、站会、结束汇报）；旁边是“现在在等你”。
- 验证：假 CLI 的集成测试（按依赖完整推进并全部合并、A 先于 B 合并、提议的条目被批准、预算用尽停止且不再派活、暂停不派活、需求类议题等人时停下、开始前的检查）；**真实 Claude 冒烟**（`crates/cli/tests/real_autopilot.rs`，极小的 Python 项目、2 个有依赖的条目、预算 12 次调用）：约 92 秒、10 次调用、$0.99，两个条目都由 bob 做完、carol 评审、评审意见被处理、依次合并，批次以“计划全部完成”结束，没有人参与。
- 顺手修的问题：策略对“工作区内的路径”的判断不识别符号链接（macOS 上 /var 与 /private/var），CLI 报告真实路径时会被误判为越权而弹审批；现在两种写法都认，旁边的目录仍算工作区之外。
- 诚实的局限：负责人这一圈目前是 **规则驱动**（流程固定），AI 负责人用在主持评审会、起草纪要、站会；还不是“AI 负责人用模型自己判断每一步该做什么”（比如自己裁决技术议题、自己调整计划、自己写文档和记忆）。这是下一步。没有真实长时间、大项目的运行验证，也没有在桌面窗口里点过。

### 20.33 负责人自己裁决技术议题

- 自主推进时，AI 负责人对**员工提议的一般技术类议题**自己拍板，不再等人。范围：类型为技术方案 / 流程 / 风险 / Bug 归因、非高风险、由 AI 员工提出（人提的议题仍由人定）；需求类、高风险、代码细节类（归议题负责人）不碰。权限沿用议题的拍板规则，核心层强制。
- 做法（`ruling.rs`）：负责人（只读、不带团队协作工具）拿到议题、候选方案、挂在议题上的会议讨论、项目目标和相关记忆，可以只读地查看代码核实事实，只能输出一个 JSON 裁决：采用第几个方案或自己的方案、最终决定、原因、没采纳的方案各自的原因；缺依据或涉及需求变更/资金/生产/不可逆/安全时必须“升级”并写明原因。输出不合格（没 JSON、方案编号越界、缺决定或原因）一律当作升级给人，不瞎猜。
- 结果：裁决写入议题（拍板人是负责人，没选的方案保留并记录原因），自动沉淀为已验证的项目决策记忆，后面的任务会自动带上；升级的议题进入“待决策”，出现在人的待办里并带着负责人写的原因；同一个议题不会在后面的批次里被反复裁决。每次裁决是一次模型调用，计入批次预算，每圈最多裁决 3 个。动态时间线里有“裁决”和“交给你”两类记录。人是纠偏者：已决议的议题不能改，要推翻就新建议题取代它，原记录完整保留。
- 验证：假 CLI 的集成测试（AI 提议的技术议题被负责人裁决：拍板人、决定、原因、选中与被否方案及原因、决策记忆；判断不了的升级为待决策；需求类和人提的议题原样不动；第二批不重复裁决）；解析与权限的单元测试；**真实 Claude**（`crates/cli/tests/real_ruling.rs`，2 次调用、$0.05）：对“store.py 保存要不要改成原子写入”（两个方案：临时文件加 os.replace、换 SQLite）选了前者，原因引用了读到的代码和项目“只用标准库、JSON 存储”的约束，并写明 SQLite 为什么没选；对“清空生产用户表、没有备份”的议题选择升级，并指出项目里根本没有这个数据库、缺依据，建议人先确认库、先备份。
- 未做：负责人自己起草和调整计划；管理记忆和文档；人提的议题让负责人在人同意下裁决。

### 20.34 负责人自己起草和调整计划

- **起草**（`planning.rs`）：计划页新增“让负责人起草计划”。负责人读项目目标（没有目标会拒绝）、扫描结果、测试基线、评估报告、成员及其角色和现有计划，输出一份 JSON 计划：1～15 个条目，每条有说明和能用命令验证的验收标准、负责人、依赖（只能依赖更靠前的条目，所以不会成环）；负责人必须是项目成员，否则整份拒绝，不会创建半份计划。条目进入“提议中”，由人在“开始自主推进”时确认——人只确认方向，不逐条写。
- **调整**：自主推进里有两个触发点——某个条目反复失败后（每批次最多 2 次）、计划全部做完后的一次完成度复盘（每批次 1 次；如果追加了条目，推进继续）。负责人可以：追加条目（每次最多 3 个，必须写原因，依赖可以指向已有条目 `#n` 或本次追加的 `N1`…）、取消还没开始或已失败的条目、改派还没开始的条目、让失败的条目换个更清楚的说明重试。完成度复盘只能追加。已开始和已完成的条目不能动；涉及目标、需求或范围变更时必须 `escalate` 交给人。追加的条目直接“待开始”并在备注里写明原因（人开始推进时已批准计划的范围）；越权或越界的改动被拒绝并写进动态。所有调整都在动态时间线里有记录。
- 验证：解析与校验的单元测试；假 CLI 的集成测试（起草的条目是提议中、负责人和依赖正确、没目标时拒绝；完成度复盘追加条目后推进继续并合并、同时提出的“取消”被拒绝；失败后调整：追加 3 个、依赖正确、坏依赖和超上限被拒绝并说明、取消、改派、重试把失败条目重置为待开始并带上补充说明）；**真实 Claude**（`crates/cli/tests/real_planning.rs`，2 次调用、$0.13）：对“把 ledger.py 迁移到 Rust、行为逐字一致”的目标起草了 7 个条目——脚手架与基准样例、CSV 解析、Python float 兼容解析、求和与 CLI、差分测试脚本、QA 对抗测试、收尾——依赖合理（解析与差分测试可并行），验收标准都是可执行的命令；条目失败（找不到 Cargo.toml）后，负责人选择“重试并补充说明”，没有乱追加或取消。
- 未做：负责人管理记忆和文档；失败重试触发的调整在循环里没有单独的集成测试（单元层覆盖了调整本身）。

### 20.35 负责人管理记忆和文档

- **文档**（`docs.rs`）：项目文档放在项目仓库 `docs/`，由负责人走和代码一样的流程维护——以负责人名义开任务分支、写文件、保存检查点、合并，提交署名是负责人。为不碰用户已有文档，负责人只写 `docs/crewforge/` 下的文件：`decisions.md`（决策记录，ADR 风格：决定、原因、拍板人、日期、取代关系、未采纳方案及原因）、`known-issues.md`（未决议题、待跟进的评审事项、受阻或取消的计划条目）、`progress.md`（计划进度）——这三份由数据确定性生成、不含时间戳、不调用模型，内容不变就不产生新提交；`overview.md`（项目概览与运行方式）由负责人读代码撰写（一次模型调用，只写核实过的事实，不确定写“待确认”）。写入路径限制在 `docs/crewforge/*.md`，读取限制在 `docs/**/*.md`；负责人手上有进行中的任务时不更新（等他做完）。
- **界面**：项目“文档”页改为左右布局——左边是主分支 `docs/` 下的全部 Markdown（负责人维护的排在前面），右边是只读阅读（轻量 Markdown 渲染，不引入依赖、不执行 HTML）；“让负责人更新文档”按钮；自主推进动态里有“更新了项目文档”。
- **记忆整理**（`curate.rs`）：已验证的记忆会注入给所有员工，所以 AI 提议、纪要总结出来的“待验证”经验需要把关。负责人逐条核实：能核实的验证（必须写依据）、过时或与代码矛盾或只是状态描述的让它过期（必须写原因）、重复的合并；拿不准的不动，留给人。**边界**：只动项目层；人写的、议题决议沉淀的、导入时确认的记忆一律不碰；每次最多 8 条改动；每条改动都写进事件和记忆的过期原因；没有待验证的记忆时不调用模型。记忆页新增“让负责人整理记忆”。
- **自主推进里的位置**：每合并 2 个任务、且待验证经验攒到 3 条以上时整理一次记忆；计划做完、完成度复盘之后收尾——整理剩余的待验证记忆、更新文档，再结束批次。每一步各是一次模型调用（文档概览 1 次、整理记忆 1 次），计入批次预算。
- 验证：解析与路径限制的单元测试；假 CLI 的集成测试（自主推进结束后 `docs/crewforge/` 下四份文档都已合并进主分支，决策记录里有被裁决的议题、原因、拍板人和未采纳方案及原因，已知问题里有升级给人的议题，提交署名是负责人；越权路径被拒绝；再次更新内容不变时不产生新提交；整理记忆只动 AI 来源的项目记忆，人写的和议题决议沉淀的不碰，不存在的编号被拒绝）；**真实 Claude**（`crates/cli/tests/real_docs_memory.rs`，2 次调用、$0.11）：对一个三文件的小项目写出了准确的概览——逐行说明 `greet` 的行为，指出了测试覆盖缺口（None、纯空白、首尾空白），并因为会话只读、没能运行测试而把相关内容明确标为“待确认”；整理记忆时验证了有依据的“运行测试的方法”，让“目前进度”（空泛的状态描述）和“依赖管理：用 poetry”（与代码矛盾，仓库里没有 pyproject.toml）过期并写明了理由，人写的约定没动。
- 未做：公司层面的文档和记忆整理；负责人主动修改已有的非 `docs/crewforge/` 文档；对话式的文档评审。

### 20.36 完整演练暴露的成本问题与三项改进

- **演练**（真实 Claude，`crates/cli/tests/real_autopilot_full.rs`）：项目是命令行待办清单 `todo.py`（只用标准库，add/list/done/rm/clear-done，JSON 存储）。负责人 18 秒起草 5 个条目；批准后自主推进约 10 分钟、48 次调用、估算 $11.49（其中开发任务 31 次 $9.46、会议 8 次、纪要 7 次、计划 2 次）、审批 0 次；6/7 个条目完成并合并，批次因“调用次数达到预算 40”（实际 47）停下，最后一个由收尾复盘追加的“修订 README 并做最终验收”没做，收尾（整理记忆、更新文档）因此也没走到。独立验收：项目自己的 80 个 unittest 全部通过；手工烟测各命令的输出格式、`rm 99` 退出码 1、坏日期退出码 2、list 的排序与 `--all` 都符合目标。站会预警了“两个任务都在改 todo.py”，后来确实冲突、由员工解决。
- **暴露的问题**：评审意见处理占了大头（每个条目约 5 条，且处理意见的调用计入开发）；并行的两个任务收到同一条意见（`load` 处理空文件/损坏 JSON）被各自改了一遍；预算 40 实际用到 47。
- **改进一：并行任务里相同的评审意见只处理一次**。比较意见文本的字符二元组 Jaccard 相似度（≥0.55 算同一件事），对象包括本批次已派出的和项目里最近已处理的；重复的驳回并写明“只处理一次，修复会随主分支合并过来”。
- **改进二：每个条目最多处理 3 条拦合并的意见**。超出的不是丢掉，而是降级为“之后再说”（`blocking = 0`，仍开着、仍被跟踪、出现在已知问题文档和“之后再说”计数里，但不拦合并、不进人的待办）。
- **改进三：软预算**。调用数或时间用到预算的 80% 后，只做必须做的（开发、验证、评审、合并）：不再处理评审意见（降级）、不再开站会、不再整理记忆；并且按本批次已合并条目的平均调用数估计，剩下的调用数不够再做一个条目时就不再开始新条目（批次以“预算”结束并说明原因），避免超出预算。
- 验证：相似度的单元测试；假 CLI 的集成测试（5 条互不相同的拦合并意见只处理 3 条、其余 2 条降级且仍开着、不进人的待办；并行任务的同一条意见只派出一次、另一条被驳回并写明重复；预算 5 时 A 做完后不再开始 B，总调用不超预算）。没有重跑完整演练（会再花约 $10 额度）。

### 20.37 员工会话上下文上限

- **问题**：员工的会话可续接、记忆连续，但上下文会一路涨；每一步都要重读整个上下文，越大越贵、越容易跑偏，缓存过期后还要整段重写（实测一次重写 716K）。
- **做法**：每次模型调用时记录上下文大小（输入 + 缓存读 + 缓存写），写进 `turn_result.context_tokens`（取本轮最后一次调用）。下次给这个员工派活前，如果上一轮超过上限（设置项 `context_limit`，默认 150000 token，0 表示不限）就换新会话：丢弃旧会话记录（历史事件保留）、记一条 `session_rotated` 事件，并在提示开头说明“上一个会话已换新，之前的对话不可见，以任务、项目记忆和工作区状态为准，先只读核对进度”。连续性由项目记忆、任务单和 git 状态承担，不靠对话。
- **边界**：上次任务异常中断（会话仍是 running）时不换，先走恢复；Copilot 员工没有上下文数据，不受影响；会议、纪要等所有走同一入口的调用都适用。
- 验证：假 CLI 的集成测试（超限后换新会话且提示带说明和旧上下文大小、新会话未超限时不再换、上限为 0 时不换），全部测试通过。
- **用量页“员工会话”标签**：列出每个员工会话的目录、状态、当前上下文、占上限的比例（≥70% 黄、≥100% 红并标“下次换新”）、最近活动和已换新次数（`usage.rs::session_contexts`）；不受时间筛选影响，随新的调用结果自动刷新。Copilot 员工显示“不提供”。
- **设置页输入框**：设置页新增“员工会话上下文上限”，以 K token 为单位，0 为不限，小于 20K 的非零值被后端拒绝（会频繁换新）；保存后下一次任务生效。同时把设置页里过时的“Copilot 适配尚未开始”改为指向“模型”页。
- 未做：界面没有点开实测（类型检查和构建通过，后端有测试）；换新会话时不做模型总结（有意：总结本身要花额度）。
- **推荐模型（第 3 条）**：“模型 → 按用途的默认模型”多了一列“Claude 推荐”和按钮“应用推荐（只填还没设置的用途）”（`models.rs::RECOMMENDED_CLAUDE`）。推荐思路：次数少、影响大的判断用强模型——负责人裁决、计划用 opus；量最大的开发任务、会议发言、文档、记忆整理、导入评估用 sonnet；纪要起草用 haiku。只在用户点按钮时写入，已设置的用途不覆盖，不动 Copilot，也不动员工自己指定的模型。没有按“角色”设默认模型：负责人的重活本来就走裁决、计划等独立用途，按用途设置更准。
- 未做：推荐值没有用真实数据验证效果（比如 haiku 写纪要的质量、sonnet 做会议发言的质量）；界面没有点开实测。

### 20.38 演练复盘后的两处改进

- **背景**：重跑完整演练（同一模型）：35 次调用、$4.78，对比上次 49 次、$12.28；软预算生效、没有超预算；但 5/8 个条目完成后收尾（整理记忆、更新文档）又因为预算用光没走到，并且三个并行条目都在改 `todo.py`，合并冲突三次，每次让员工解决要多花调用。
- **预算留收尾**：开始新条目前先从剩余调用数里扣掉 3 次（`WRAP_UP_RESERVE`），原因里会写明；因为“扣掉收尾后不够再做一个条目”而停下时，照常做收尾（整理记忆、更新文档），然后再以“预算”结束。真正的硬预算（调用数或时间用光）仍然直接停，不再追加调用。
- **同一个文件不并行**：计划条目新增 `files`（迁移 15）——负责人起草或追加条目时列出它预计会改的主要文件，并被提示“尽量让不同条目改不同的文件，实在要改同一个就合并成一个条目”。自主推进派活时，预计会改同一个文件的条目排成先后，不再并行（没写 files 的条目不受限）；这是顺序约束，不是依赖，不改变条目的前置关系。
- 验证：解析的单元测试；假 CLI 的集成测试（预算停下时仍写了文档且没超预算；对照组不写文件时 A 与 C 并行、都声明改 `shop.py` 时不并行且都完成）。**没有再跑真实演练**（再花约 $5）。
- 未做：`files` 只由负责人声明，没有从实际改动里校验（声明漏了仍可能冲突）；界面没有显示条目的 files。
- **真实演练验证**（`todo-cli-3`，同一模型、同一预算）：负责人起草 5 个条目，**每个都填了 `files`，且各改各的文件**（`todo.py`、两个测试文件、README 与 .gitignore、QA 的边缘用例）；复盘时追加 2 个条目（修 `todo.py`、QA 收尾），它们改的文件也都写了。35 次调用（含起草共 36）、$5.87，6/7 完成，**合并冲突 0 次**（上次 3 次），并行只发生一次（README 与测试，改不同文件）。因“扣掉收尾后预算不够”停下，**收尾照做了**：写出 `docs/crewforge/` 下 4 份文档（概览如实标了“没运行测试，待确认”）。项目自己的 47 个 unittest 全部通过，烟测各命令输出和退出码都对，审批 0 次。一个条目验证未通过一次，员工修好后合并。
- **要保留的疑问**：这次零冲突有一部分是计划本身分得好（先写一个条目实现全部命令，再并行写测试），不能全算在“同文件不并行”上——这次没有出现两个条目声明改同一个文件而且本可以并行的情形，所以这条规则本身在真实模型下没被触发过，只有假 CLI 的测试验证。费用比上一次略高（$5.87 对 $4.78），因为这次多追加了 2 个条目；三次对比：$12.28（49 次）→ $4.78（35 次）→ $5.87（36 次）。
- 演练测试的结尾断言改为接受“预算”结束（不再把正常的预算停止当成失败）。

### 20.39 行动项按钮的两处问题

- **已结束会议里还能看到“已处理 / 驳回”**：这是有意的，不是 bug——行动项属于项目，不随会议结束而消失；评审会议里“合并前”的行动项还会拦住对应任务的合并，所以会议结束后仍要能处理。只有已处理、已驳回或已撤回的才不再显示这些按钮。
- **“驳回”点了没反应**：原因是 WebView 里没有 `window.prompt`（调用直接返回 null）。用它的地方有三处——行动项驳回、记忆标记过期、计划条目阻塞——全部改为就地展开输入框的 `ReasonButton`（驳回要求必须写原因，Enter 确认、Esc 取消）。
- **“交给 TA 处理”点了没反应**：员工正在执行任务时后端会拒绝（“X 正在执行任务，请等待完成”），但这条提示只出现在窗口顶部的提示条里，容易看漏；并发已满或额度紧张时任务进入排队，而行动项要等真正开始才变成“处理中”，中间看不到任何变化。现在派活的结果就地显示在这一项下面：失败写明原因（红字），成功写“已派给 X，开始处理后会变成处理中，并发已满或额度紧张时会先排队”。
- 未做：员工在忙时直接禁用按钮（界面这一层还没有拿到运行中的员工列表）；排队中的状态没有单独标记在行动项上。界面没有点开实测。

### 20.40 结束项目：已完成 / 归档 / 不做了

- **入口**：项目页“成员”下方的“项目信息”旁，“结束项目…”（取代原来藏在最底部的“归档项目”）。弹窗里三选一，都可以写原因。
- **已完成**：要求所有任务都已合并或放弃（有进行中的任务就拒绝，并提示改选“归档”）；只做标记，什么都不删。
- **归档**：标记项目结束；进行中的任务自动放弃（改动保存为 WIP，分支和工作区都保留）；任何目录都不动。
- **不做了（彻底删除）**：先全部校验再动手——必须输入完整的项目名称；员工的 worktree（只清理数据目录下由 Crewforge 建的）、任务分支、员工在该项目里的会话记录、项目的全部记录（成员、任务与检查、会议与发言、议题与选项、计划与依赖、行动项、记忆、基线、扫描、导入报告、自主推进批次、非用量事件）在一个事务里删除，失败整体回滚。**用量记录（`turn_result`）保留**，因为那是真实花掉的额度。员工本身（公司的人）不受影响。同一目录之后可以再登记为新项目。
- **删除项目文件夹**（可选勾选）：只允许 Crewforge 新建的项目；导入的已有项目拒绝（界面上禁用，只清理 Crewforge 里的内容）；目录必须是干净的 Git 仓库（有未提交改动拒绝，并列出文件）；拒绝过浅的路径、家目录及其上级、与数据目录有包含关系的目录；移到 `~/.Trash`，不是永久删除。
- **恢复**：公司 → 项目页底部“已结束的项目”列出已完成/已归档的项目（状态、原因、时间），可恢复；被放弃的任务不会自动恢复。早期归档的项目按“已归档”显示。“不做了”的不能恢复。
- **安全**：结束前先通知自主推进停下，并要求项目成员此刻没有人在执行任务，否则拒绝并说明。数据库迁移 16（`end_kind`、`end_reason`、`ended_at`）。
- 验证：集成测试 3 个（已完成拒绝有进行中任务的项目、归档放弃任务且目录都保留、可恢复；彻底删除要求完整名称、清理 worktree 与分支与全部记录、保留文件夹和用量记录、员工保留、目录可再登记；删文件夹时有未提交改动拒绝且什么都没删、导入项目拒绝、干净的新项目移到废纸篓）。界面没有点开实测。
- 未做：删除项目时不清理 JSONL 事件日志里已有的行（那是审计记录）；没有“清空废纸篓”之类的后续动作。

### 20.41 全局前进 / 后退与通知面板

- **通知面板**：点面板以外的地方或按 Esc 关闭（原来只能再点一次铃铛）；点铃铛仍然是开关，点面板里面不关。
- **全局前进 / 后退**（`ui/src/useNav.ts`）：像浏览器一样记录“位置”的变化——切换公司 / 项目 / 模型 / 用量 / 设置，以及公司页和项目页里切换标签——可以回退和前进；后退之后去了别处，前进历史丢弃；回退到已经不存在的位置（比如被结束的项目）时自动跳过；最多 60 条。触发方式：顶栏左侧的 ‹ › 按钮（不可用时置灰）、**鼠标侧键（后退 / 前进，如罗技 MX Master 3 的拇指侧键，即鼠标按键 4、5）**、Cmd+[ 和 Cmd+]。
- 验证：在浏览器里用 puppeteer 实测——鼠标后退 / 前进键、Cmd+[ / ]、顶栏按钮的回退序列都对，前进历史被正确丢弃，通知面板点外面 / Esc / 再点铃铛 / 点里面的行为都对。**没有在真正的桌面应用（WKWebView）里用实体鼠标测过**：浏览器里侧键事件是 button 3/4，WebView 一般同样如此，但罗技的驱动可能把侧键映射成别的按键。如果侧键没反应，在 Logi Options+ 里把前进 / 后退键设为“后退 / 前进”，或设为键盘快捷键 Cmd+[ 和 Cmd+]（本应用已支持）。
- 未做：记录的只是“位置”（范围 + 标签），不含更细的状态（滚动位置、选中的会议或议题、展开的面板）。

### 20.42 “待你处理”要能找到具体的事

- **问题**：小铃铛显示“2”，进项目后只看到“2 件事需要你决定”的一行汇总，点“去处理”只是跳到会议页签，而会议页里有很多场会议，找不到是哪两条、在哪场会议里。
- **改法**：“我的职责”里，需要人来决定的行动项**每一条单独列出**（完整的原文，最多 120 字），说明来自哪场会议、该怎么处理，“去处理”直接打开那场会议，在纪要下方的行动项里点“已处理”（或写明原因后“驳回”）。数字与小铃铛一致（每条算 1）。
- 验证：单元测试（两条人类行动项分别列出、都指向所属会议、数字合计为 2、不是给人的那条不出现）。界面没有点开实测。
- 未做：小铃铛面板里的“行动项”仍是按项目汇总（点“看详情”进职责页再逐条处理）；评审意见（拦合并的）和待合并的任务仍是汇总行。

### 20.43 标给人的行动项由负责人先处理

- **问题**：纪要里 AI 把一些事标成“人类”，进了人的待办；但按分工，只有需求变更、高风险操作、架构取舍才该由人拍板。实测的两条（棋盘填满要不要区分胜负、回车重开后要不要直接开始）都是界面和实现细节，后一条需求原文已经写明。人还要自己判断“要不要改代码”，并且点“已处理”之后没有任何人去做。另外，贪吃蛇项目没有 AI 负责人（按规则由人担任），所以这些事全落到人手里。
- **收紧标给人的标准**（纪要起草的提示）：只有需求变更、高风险操作（删除数据、生产、资金、安全）、架构取舍三类才写“人类”；界面细节、实现取舍、实现与需求原文是否一致由负责人或员工决定。
- **负责人先处理**（`lead_actions.rs`）：负责人读行动项、所在会议的纪要、项目目标和需求原文、项目记忆、成员和现有计划，只读地看代码，输出结构化结果——`decide`（决定 + 依据 + 最多 2 个后续计划条目，写明负责人、验收标准、预计改的文件）、`dismiss`（不必做，写明原因）、`escalate`（必须是人：需求变更、业务方向、资金、生产、不可逆、安全、架构取舍，或缺少无法核实的关键信息，写明为什么）。结果：决定 → 行动项标为已处理并写下“负责人决定：…（依据：…）”，后续条目直接进计划（待开始，不再等人批准）并带 `files`，沉淀为已验证的项目决策记忆；驳回 → 写明原因；升级 → 行动项留着、写上负责人为什么认为必须是你，记事件，之后不再反复问；回复格式不对 → 同样留给人并写明。
- **触发**：自主推进每轮在裁决议题之后处理，每轮最多 3 条，软预算之后跳过；职责页“现在在等你”旁有“让负责人先处理”按钮（最多 5 条）。没有 AI 负责人时无法处理，需要先在“成员”页指定。
- 验证：解析的单元测试；假 CLI 的集成测试（决定：追加条目含文件、不存在的负责人不指定而不是整条丢掉、记忆为已验证的决策；驳回；升级且不再被反复问；格式错误交给人）；**真实 Claude**（`crates/cli/tests/real_lead_actions.rs`，1 次调用约 $0.1）：把贪吃蛇的负责人设为 Alice 后，她对“回车重开”这条决定“照需求原文办，结束后按回车直接开始新一局”，写明依据（需求原文、待机状态是后加的行为、首次开局保留待机不受影响），追加了一个计划条目（改 `restart`、补测试、更新 README，文件 `src/lib.rs`、`src/game.rs`、`web/main.ts`、`README.md`）。
- 未做：纪要标准收紧后没有用真实会议验证 AI 是否还会乱标；升级的事项在职责页里还不单独显示“负责人为什么留给你”（写在行动项的备注里）。

### 20.45 员工在忙时不能派活，按钮直接说明
- 会议页行动项的“交给 TA 处理”：所选员工正在执行任务（`running` 里有他）时按钮置灰，悬停提示和按钮下方都写“X 正在执行任务，做完后才能派给 TA（或换一个负责人）”；换一个不忙的负责人就能点。之前是点了才由后端拒绝，提示还只出现在顶部提示条里。
- 未做：排队中的状态没有单独标在行动项上（派出后只有“已派给 X，并发已满或额度紧张时会先排队”的说明）。界面没有点开实测，类型检查通过。

### 20.47 验证“标给人”的收紧标准（第五次真实演练）
- `todo-cli-5`（同一模型、同一预算）：33 次调用（含起草 34）、$4.59，**计划 5/5 全部完成**，项目自己的测试通过，收尾做了。

- **能说明和不能说明的**：能说明这个项目这种复杂度下，收紧后的纪要标准没有再把事情标给人；不能说明标准在模棱两可的情形下（比如界面细节、实现与需求是否一致）也管用——触发过这个问题的贪吃蛇有更多产品细节，todo-cli 太简单。收紧之前的对照数据随着被删除的演练项目丢失，所以也无法说明“比以前少”。兜底路径本身由假 CLI 的测试和一次针对贪吃蛇真实行动项的真实调用验证过（20.43）。
- **顺带发现的问题**：评审里“之后再说”的行动项没人跟进，会一直积累——第 4 次演练结束时有 45 条处于待处理（不拦合并），第 5 次演练约 23 条。它们不进人的待办、不拦合并，但没有任何环节去清理或处理，项目做长了会越积越多。需要一个处理机制（比如负责人在收尾时批量处理：合并相似的、驳回不必做的、把值得做的变成计划条目）。

### 20.48 负责人整理“之后再说”的行动项
- **问题**：评审里不拦合并的意见降级成“之后再说”后，不进人的待办、也没有环节处理，会无限积累（演练里一个项目做完有 45 条、另一个 23 条）。
- **做法**（`lead_triage.rs`）：积累到 5 条以上时，负责人逐条过一遍（最多 60 条），读需求原文、项目成员、现有计划，只读地核实代码，输出每条的处理：`dismiss`（重复、已被解决、过时、过度设计、没价值——必须写原因，重复的写和哪一条重复）、`plan`（值得做的转计划条目，每次最多 3 个，写验收标准、负责人、预计改的文件，相近的合成一个，对应行动项标为已处理并写明转成了哪个条目）、`keep`（拿不准的保留）；没提到的原样保留；给人的行动项和拦着进行中任务合并的行动项不在范围内；编号不存在或重复出现的指令被拒绝并写进动态；所有改动写进事件。
- **触发**：自主推进收尾时（整理记忆之后、更新文档之前）自动做；收尾预留的调用数从 3 次调整为 4 次；职责页“另有 N 条‘之后再说’”旁有“让负责人整理”按钮（5 条以上才出现）。
- 验证：解析的单元测试；假 CLI 的集成测试（不够 5 条不调用模型；驳回带原因、转计划带文件和负责人、保留、没提到的不动、给人的不动、坏编号和重复编号被拒绝）；**真实 Claude**（`crates/cli/tests/real_lead_triage.rs`，1 次调用约 34 秒）：对第 4 次演练项目积累的 45 条，负责人驳回 28 条、转成 3 个计划条目（加固 add、修复 list 对空 due 的排序、收尾 README 与端到端测试，都带文件和负责人）、保留 14 条，没有被拒绝的指令；抽样的驳回原因都具体且核实过（“已含‘就地修改 data’，无需再改”“已解决：.gitignore 含 __pycache__/，store.load 捕获 JSONDecodeError…”“计划 #1–#7 全部已完成，不再有合并先后问题”）。注意：这次真实调用直接改动了该演练项目的数据。
- 未做：自主推进里整个收尾流程（整理记忆、整理行动项、更新文档）的端到端真实演练没有重跑；整理的质量只在这一个项目上看过，没有人工逐条复核 28 条驳回是否都正确。

### 20.49 行动项页
- **问题**：行动项只能在各场会议的纪要下面看，要找“有没有没解决的”得一场一场点开会议。
- **做法**：项目页新增“行动项”标签（`ActionsView.tsx`），集中列出项目里全部行动项（新的在前，不含从纪要里撤回的）。**状态筛选**：未处理（默认）、已处理、已驳回、全部，各带数量；**类型筛选**（只针对未处理）：给你的、拦合并、之后再说，各带数量；切到非“未处理”时类型筛选自动清掉。每条显示类型、状态、负责人、来自哪场会议、备注，可以直接处理：交给 TA 处理（员工在忙时置灰并说明）、已处理、驳回（必须写原因）、重新打开；“打开会议”跳到所在会议并高亮那一条。“我的职责”里“之后再说”的提示也指向这个页面。
- 验证：浏览器里用模拟数据实测筛选和计数（未处理 3 条、给你的 1 条、切换状态）；类型检查通过；后端只加了一个按项目列出全部行动项的查询。没有在桌面应用里用真实数据点过。
- 未做：标签上没有未处理数量的角标；不能按负责人或会议筛选、不能搜索；批量操作（比如一次驳回多条）。
