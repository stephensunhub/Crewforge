# 设计草案：统一模型（需求 · 计划 · Bug · 排期 · 文档）

> 状态：**已按本文实现（第 1–3 步）**，实现时与本文有几处出入，见文末「实现时的调整」。
> 背景：项目上线后要持续维护，需求会迭代、bug 会出现、文档会演进。现在的 bug 流程、规格库、定时任务、公司总览是分别加上去的，概念之间是割裂的。本文把它们放进同一个模型里。

## 1. 要解决的问题

1. 没有需求入口：需求从哪来、谁评估、采纳后怎么变成计划，没有地方回答。
2. 没有一条把**所有人的所有事**排成先后顺序的时间线：QA 报了 bug 谁来安排、开发正在干别的什么时候回来修，没有地方回答。
3. Bug 没有自己的生命周期，也没有「谁开发的谁修」「修完谁复测」。
4. 文档只反映「当下」，看不出需求、架构怎么演变；项目文档和功能规格没有分清。
5. 行动项、议题、会议、定时器、总览各是一块，互相不知道对方。

## 2. 原则

- **沿用现有名称，不改名**：「计划」（项目管理侧：拆成有依赖的条目）和「任务」（员工在分支上的一次执行）保持现状。只给新增的东西起新名字。
- **负责人（AI）兼任产品经理和排期人**，不新增角色。「评估需求」「做计划」「排期」本身也是计划条目，出现在排期表里。
- **排期不预测日期**，只记录顺序、前置、阻碍，以及「什么时候因为什么被排进来」。
- **排期驱动执行**：自主推进只派已排期、且前置满足的条目；没排期的不会被自动派。
- **两个入口，对称**：需求从「需求池」进计划，bug 从「Bug 池」进计划；之后都由负责人排期。
- **文档分两类**（照搬 Kiro 的划分）：项目文档（长期背景）和功能规格文档（随功能演进）；每份文档都有版本列表。
- **成本原则**：新概念只是记录和视图，不是新调用——QA 在测试那一轮里顺手记 bug（一次工具调用），开发本来就要修，文档只是分类。唯一新增的调用是**排期**，而且只在**存在未排期条目时**才发生（见 4.5）。对齐会只管防止目标漂移，不承担排期。
- 能从数据确定性生成的，不让模型写。

## 3. 概念与关系

```
项目目标 ─────────┐
需求池（人 / QA / 员工提交）──负责人评估──▶ 需求（采纳后）──── 规格文档（需求、设计）
                                              │ 负责人拆分
                                              ▼
Bug 池（QA / 人）──负责人确认──▶ ┌─────────────────────────────────────┐
定时器 ──到点──────────────────▶ │ 计划条目（有依赖、有类型）            │
评审意见 [之后] ───────────────▶ │ 类型：评估 · 架构 · 开发 · 测试 · 文档 │
                                 │       回归 · 复测 · 修复 · 检查 · 排期 │
                                 └─────────────────────────────────────┘
                                              │ 负责人排期（有未排期条目时）
                                              ▼
                          排期表：未排期 ⇄ 已排期 → 执行 → 完成
                                              │ 派给员工
                                              ▼
                          任务（员工的一次执行：分支、diff、合并，不变）
评审意见 [合并前] ──────────▶ 挂在被评审的任务上，拦合并（不变）
```

| 概念 | 界面名称 | 说明 |
|---|---|---|
| 需求 | **需求**（新增） | 产品侧：做什么功能、为什么；有规格文档 |
| 计划条目 | 计划（不变） | 现有 `plan_items`，加「类型」「所属需求」「来源」「是否已排期」 |
| 执行 | 任务（不变） | 现有 `tasks` |
| 排期 | **排期**（新增） | 全部条目的时间线表格 |
| Bug | **Bug**（新增） | 独立栏目 |

「需求」的叫法是新增的，现有名称一概不动。

## 4. 各对象

### 4.1 需求（新表 `requirements`）

**一个需求同时包含业务面和技术面，不拆成两种需求**：业务面写做什么、为什么、验收标准（AC-n）；技术面写怎么做、用什么、约束。两者在同一个需求、同一份规格里（`requirements.md` 写业务面，`design.md` 写技术面），一起拆成计划条目。条目同时引用 AC 和设计章节，可追溯。

- 技术面里**人指定的技术要求**（如「必须用 sa-token」）标注来源「人指定」，是硬约束：架构师和员工不能推翻，发现不可行时升级给人。架构师自己提的是建议，可以修订。
- 全项目的技术约束（统一鉴权框架、语言栈）不属于某个需求，放项目文档「背景与约定」和「架构」，需求只引用。
- 没有业务面的纯技术改进（升级框架、清理技术债），类型为「技术改进」，只有技术面。

字段：标题、说明、类型（功能 / 技术改进）、来源（人 / QA / 员工 / 目标拆分）、状态、优先级、规格目录、提交人。

状态：`待评估` → `已采纳` → `规格中` → `实施中` → `已交付`；另有 `搁置`、`拒绝`（必须写原因）。

- **需求池**就是「待评估」的需求，人、QA、其他员工都可以提交（一个输入框，业务和技术混着写都行；另有可选的「人指定的技术要求」栏）。
- 评估（采纳、搁置、拒绝、合并）**在排期调用里一并做**（待评估的需求也是「未排期」的输入，见 4.5），不单独调用。
- 采纳后先产生规格条目（需求规格、设计），文档合并后再拆实现条目——这是现有的功能规格流程，改为挂在需求上。
- 需求页和计划页互相可跳转；需求之间可以有依赖。项目目标的变更仍走「目标变更提议，人批准」。

### 4.2 计划条目（现有 `plan_items` 扩展）

新增字段：
- `task_type`（取代现在的 `kind`，旧值映射：migrate→开发，characterize→测试，cleanup→开发，design→架构，bugfix→修复，spec→文档，other→开发）。类型：`评估`（评估需求、做计划）· `架构` · `开发` · `测试` · `文档` · `回归` · `复测` · `修复` · `检查`（定时器产生）· `排期`。
- `requirement_id`：属于哪个需求（取代刚加的 `spec_id`）。
- `bug_id`：由哪个 bug 产生。
- `source`：目标拆分 / 需求 / bug / 定时器 / 评审意见 / 负责人追加 / 人添加。
- `schedule_state`：`未排期` / `已排期`（见 4.4）。

状态沿用：待确认 / 待开始 / 进行中 / 已完成 / 已阻塞 / 已取消。依赖沿用 `plan_deps`。

### 4.3 Bug（新表 `bugs`，独立栏目）

字段：标题、严重程度、复现步骤、期望行为、实际行为、**不应改变的行为**（借鉴 Kiro 的 bugfix spec，用来划定回归范围）、补充信息、来源（QA / 人 / 员工）、出自哪个条目（`origin_item_id`）、责任开发（`owner_id`）、优先级（P0–P3，负责人定）。

状态：`新报告` → `已确认` → `修复中` → `待验证` → `已关闭`；出口：`无法复现`、`重复`（写明和哪个重复）。

- **谁记**：QA 通过团队工具 `report_bug` 记（要求带复现步骤）；人在 Bug 栏目手动加，表单同现在的。
- **谁修**：默认是做了 `origin_item` 的那位员工；没写出处或那人已离开，由负责人指派。
- QA 记下 bug 的同时，代码按严重程度给出**默认优先级**（阻断 P0、严重 P1、一般 P2），并自动生成一个**修复条目**（指派给责任开发）和一个**复测条目**（前置是修复条目）。**有 QA 时由 QA 复测，没有 QA 时由负责人复测。**这些都不调用模型。两个条目进入「未排期」，在下一次排期调用里由负责人定位置，也可调整优先级。
- **关闭条件**：复测通过。没通过 → bug 回到 `修复中`，并产生新的修复条目。
- 排期时若责任开发正忙，修复条目排在其当前条目之后，排期表上标「等 X」。

### 4.4 排期表

**排期记录**（新表 `schedule_entries`，只追加）：`item_id`、`seq`（顺序号）、`lane`（角色：产品 / 开发 / 测试 / 文档…）、`scheduled_at`（真实时间）、`scheduled_by`（负责人）、`trigger`（排期调用 / 规则兜底 / 人调整）、`reason`、`after`（前置条目）、`blocked_by`（阻碍及原因）、`action`（排入 / 重排 / 开始 / 完成 / 阻塞 / 解除）。

**页面（表格，横竖清晰）**：

| 序号 | 排入时间 | 事项 | 类型 | 角色 / 负责人 | 前置 | 状态 | 阻碍 | 触发 |
|---|---|---|---|---|---|---|---|---|
| 1 | 09:30 | 架构设计 | 架构 | 架构师 | — | 完成 10:02 | — | 排期调用 |
| 2 | 10:03 | 模块 B 开发 | 开发 | 小明 | 1 | 进行中 | — | 条目 1 完成 |
| 3 | 10:03 | 模块 C 开发 | 开发 | 小红 | 1 | 进行中 | — | 条目 1 完成 |
| 4 | 11:00 | 修复：导出崩溃 | 修复 | 小明 | 2 | 已排期 | 等小明做完 #2 | QA 报 bug（P1） |

- 分两个区：**已排期**（有序、可展开历史）和**未排期**（待办池，按类型 / 来源筛选）。
- 可按角色筛选，也可切换成「按角色分栏」；有阻碍的行高亮并写明原因（等前置 / 等人 / 同一文件冲突 / 等你确认 / 预算用尽）。
- 你可以上下移调整顺序，或把行拖回未排期；调整会记为一条「人调整」，负责人下次排期时遵守。
- 已完成的行保留，表格同时就是项目的**时间线记录**。

### 4.5 排期规则

**触发：只要存在未排期的条目，就问负责人怎么排；没有就不问。**

- **谁排**：项目负责人（AI）。一次排期调用是一个 `排期` 类条目（出现在排期表里，用量可核算）。
- **一次处理全部**：把当前所有未排期的东西（新条目、新 bug 的修复 / 复测条目、定时器产生的检查、评审意见 `[之后]`、待评估的需求）一起交给负责人，一次调用，不是每件事一次。
- **输入**：全部未排期条目、已排期但未开始的条目（可调整）、各人当前在做的事、依赖、阻碍、优先级、预算、待评估的需求。
- **输出**：结构化 JSON（沿用现有格式重试机制，最多 3 次）：每个条目的位置、角色 / 负责人、前置、阻碍原因、理由；对待评估的需求给出采纳 / 搁置 / 拒绝（写原因）。校验：依赖不成环、指派的是项目成员、不改已完成 / 进行中的条目。
- **何时发生**：自主推进在运行时，循环每次发现有未排期的条目就排一次；进行中的任务不受影响，排好前已排期的条目照常执行。自主推进没在运行时不调用；批次开始时若有未排期的，先排一次；你也可以点「请负责人排期」。
- **兜底**：连续 3 次格式不对，或没有 AI 负责人时，按代码规则排（P0 bug 插到下一位，P1 排在普通条目前，其余按计划顺序追加），并写明原因，不会卡住；没有 AI 负责人的项目由人自己在表里排。
- **执行**：自主推进只派 `已排期` 且前置满足、负责人空闲的条目；互不依赖的可并行（受并发限制，文件冲突规则不变）。P0 bug 不被「设计阶段」挡住。
- 对齐会不参与排期。

### 4.6 行动项（不再作为独立概念）

现在行动项把三种东西混在了一起：

| 现在的行动项 | 新归宿 |
|---|---|
| `[合并前]`：拦住被评审任务的合并，在同一分支继续修 | **评审意见**，挂在被评审的任务上（任务页显示），仍然拦合并 |
| `[之后]`：以后再说的事 | 直接成为**未排期计划条目**（来源「评审意见」），由负责人在排期调用里决定做不做；现在单独的「负责人整理积压的行动项」那次调用去掉，并入排期 |
| 需要人定的事 | 议题 / 人工介入中心 |

迁移：保留 `action_items` 表和已有数据，只是界面上去掉「行动项」标签，新产生的按上表分流。

### 4.7 定时器

沿用对齐会的配置形态（开关、间隔、主持人）。同一个「定时器」栏目里放：对齐会 + 预置的检查类定时（依赖与安全检查、测试健康检查、文档一致性检查、每日构建冒烟）。**全部预置好，默认关闭，由你决定启用**。到点产生的是 `检查` 类**未排期条目**，在下一次排期调用里由负责人排期（现在是直接进计划）。

## 5. 文档

分两类，沿用 Kiro 的划分：长期的背景 vs 随功能演进的规格。

### 5.1 项目文档（固定 5 份，`docs/`）

| 文档 | 回答什么 | 谁更新 |
|---|---|---|
| 架构（`architecture.md`） | 现在的系统是怎么划分的 | 架构师 |
| 决策（`decisions.md`） | 为什么这样选，放弃了什么 | **系统自动生成**：议题裁决、被否决的方案和原因、目标变更 |
| 风险（`risks.md`） | 已知风险与技术债、状态 | 负责人 + 风险类议题 |
| 项目背景与约定（`background.md`） | 产品是什么、目标与硬性约束、技术栈、术语 | 负责人 |
| 文档与代码规范（`conventions.md`） | 命名、目录、风格、测试、文档约定 | 架构师 |

现有的 `architecture.md`、`conventions.md`、概览、状态等自动文档按此重整：概览并入背景，状态并入排期表和总览。

### 5.2 功能规格文档（每个需求一个目录）

`docs/specs/<名>/requirements.md`（bug 用 `bugfix.md`）、`design.md`。**不单独写 tasks.md**：规格页上的条目列表由该需求关联的计划条目生成。

### 5.3 版本列表

每份文档（项目文档和规格文档）都有一个**版本列表**：版本号、时间、改了什么、为什么、关联的条目 / 议题 / 需求、谁改的。

- **权威来源是 git 历史**：该文件的每次合并是一个版本，关联信息取自合并的任务，不靠模型写，不会漂移。界面在文档页右侧显示，可点开看每个版本的 diff。
- 「为什么改」：条目的说明就是原因；规格和决策类文档另外要求员工在文末「变更记录」写一行原因（模型写，但只作为补充）。

### 5.4 与项目记忆的关系

不重合：文档是长文、按需读、在仓库里；记忆是一两句、每次任务自动带上、在库里。规格里「全团队都要遵守」的少数结论提炼成记忆；与规格冲突的旧记忆，在整理记忆时标为过期（对该功能以规格为准）。

## 7. 数据迁移

- 迁移 27：新增 `requirements`、`bugs`、`schedule_entries`；`plan_items` 加 `task_type`、`requirement_id`、`bug_id`、`source`、`schedule_state`；已有条目：`task_type` 按旧 `kind` 映射，`schedule_state` 设为已排期（保持现有自主推进行为），`spec_id` 数据迁到 `requirement_id`。

## 8. 不做什么（本轮）

- 不预测日期和工时；不做甘特图。
- 不新增产品、市场等角色。
- 不对接 GitHub issue / PR。
- 不做跨项目的排期（总览只汇总）。
- 不改「计划」「任务」的名称。

## 9. 分步实现

1. **统一模型**：迁移 27、需求与需求池、条目类型与排期状态、Bug 栏目（含 QA 的 `report_bug`、复测闭环）、排期表页面、负责人排期（有未排期条目时调用，一次处理全部）、自主推进改为按排期派活、行动项分流。
2. **文档重整**：项目文档固定 5 份（含自动生成的决策文档）、规格并入需求、版本列表、记忆冲突规则。
3. **定时器栏目**：对齐会与预置检查放一起、默认关闭、产出未排期条目。

每步完成后都跑全部测试，并在界面里过一遍再装。

## 10. 待确认

已定：
- 命名不改：「计划」「任务」保持现状，只新增「需求」「排期」「Bug」。
- 一个需求同时含业务面和技术面，不拆两种。
- 行动项按 4.6 分流。
- 复测：有 QA 由 QA，没有 QA 由负责人。
- 排期：存在未排期条目时才调用负责人，一次处理全部；对齐会不参与。

待定：
1. 版本列表以 git 历史为权威（5.3）。
2. 自主推进运行时，一发现未排期就排一次，会不会太频繁？可加「至少间隔 N 分钟」或「积累到 K 条或有人空闲时再排」。

## 11. 实现时的调整

1. **类型沿用 `kind` 列**，没有新加 `task_type`：在原有的 `migrate / characterize / cleanup / other / design / bugfix / spec` 上只加了 `retest`，界面上用中文名显示，避免大面积改代码。
2. **已排期是默认值**：数据库里 `plan_items.schedule_state` 默认 `scheduled`，所以人在计划页建的条目、负责人起草的计划、规格拆出的实现条目都直接已排期，老项目行为不变；只有**新来源**的条目进「未排期」：bug 的修复和复测、定时器、评审意见里“之后再说”的事。
3. **没有 AI 负责人时按规则自动排**（而不是等人手动排），否则自主推进会没活可派；人仍可在排期表里调整或退回未排期。
4. **「需求」复用了刚做的规格表**（`specs` 改名为 `requirements`，加了类型、来源、状态、人指定的技术要求），迁移 27 同时把 `plan_items.spec_id` 改名为 `requirement_id`。
5. **行动项**：`[合并前]` 仍拦合并，标签页改名「评审意见」；`[之后]` 直接变成未排期条目（来源「评审意见」，指给负责人的不带指派），**负责人整理行动项那次模型调用不再自动发生**（`lead_triage_later` 的代码保留，只是自主推进不再调用）。
6. **项目文档的五份映射到已有文件**：架构 `docs/architecture.md`、决策 `docs/crewforge/decisions.md`、风险 `docs/crewforge/known-issues.md`、项目背景与约定 `docs/crewforge/overview.md`、文档与代码规范 `docs/conventions.md`。没有的显示“未建立”。`progress.md` 留在「其他文档」。
7. **版本列表**用 `git log --follow` 生成，点一行看该版本的 diff；设计模板里要求文末加「变更记录」节（补充，不是权威）。
8. **排期记录表** `schedule_entries` 只记排入、重排、人调整、退回未排期；开始和完成的时间不单独记，排期表上用条目的状态和最后更新时间显示。
