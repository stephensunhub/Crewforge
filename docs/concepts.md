# 核心概念

读完这篇，你应该能看懂界面里每个名词是什么、有什么用、它们之间是什么关系。每个功能怎么操作见 [功能总览与典型流程](features.md) 和 [使用指南](user-guide.md)。

## 一张图看关系

```
公司 ── 员工（AI）
  └── 项目（一个 git 仓库）
        ├── 成员 = 员工 + 项目角色（负责人 / 开发 / QA / 评审 / 架构师）
        ├── 目标与硬性约束            ← 只有人能批准修改
        │
        │   做什么                      怎么安排                    谁来做
        ├── 需求 ──拆出──▶ 计划条目 ──排入──▶ 排期 ──派活──▶ 任务（worktree + 分支）
        │     │                ▲                              │
        │     └─规格文档       │ 修复 / 复测条目               ├─ 验证 → 评审 → 合并
        │                      │                              └─ 放弃（保留 WIP）
        ├── Bug ───────────────┘
        ├── 定时器 ──到点生成条目──▶ （未排期）
        ├── 评审意见 ──"之后再说"──▶ （未排期）
        │
        ├── 议题 / 会议 / 对齐会         ← 讨论、裁决、防跑偏
        └── 记忆 / 文档                  ← 沉淀与演进
```

一句话串起来：**需求（做什么）→ 计划条目（拆成具体工作）→ 排期（决定先后）→ 任务（员工的一次执行）→ 合并进主分支**。Bug、定时器、评审意见产生的活，不会直接开干，都先进「未排期」，由排期统一安排。

## 角色类概念

### 员工
一个 AI 工作者，本质是 Claude Code 或 GitHub Copilot 的 CLI 子进程，带一段身份说明和一个模型。员工之间互相独立：各有自己的会话和工作区，不共享上下文，只通过群聊、议题、记忆和 git 协作。

- **名字和编号：** 名字可改；编号（界面里 `#N`）自增，内部 ID 不变。
- **LLM 通道：** 本机订阅（用你已登录的 Claude Code / Copilot），或自建端点（如局域网里的 Ollama）。见 [连接本地模型](endpoints.md)。
- **能力上限（1–5）：** 这位员工最多能胜任几级的活。默认按模型自动给（本地模型 2，Haiku 3，Sonnet 4，Opus 和 Fable 5），可手动改。

### 项目与项目角色
项目对应你磁盘上的一个 git 仓库。员工加入项目时有一个**项目角色**，同一员工在不同项目里可以是不同角色：

| 角色 | 职责 |
|---|---|
| 负责人（lead） | 排期、派活、评估需求、裁决议题、判断是否评审、整理记忆、失败后调整计划 |
| 开发（developer） | 按条目写代码、跑测试；谁做的功能，bug 默认还由谁修 |
| QA | 验证和测试，发现问题记 Bug、复测；不写功能 |
| 评审（reviewer） | 代码评审 |
| 架构师（architect） | 只做设计和规格，不写代码，只改 `docs/` 下的 Markdown |

负责人可以是 AI，也可以是你自己。**有 AI 负责人时，决策权跟着它走**：排期、议题裁决、需求评估都由它定。你只保留：危险命令审批、删除项目、预算、批准目标变更。没有 AI 负责人时，待决定的事才交给你。

没有专门的 QA 时，复测由负责人做；没有架构师时，规格由开发写。

## 做什么：目标、需求、计划

### 目标与硬性约束
项目级的一段文字：要达到什么、技术栈、不做什么、怎么验收。每个新任务开始都会带上它，所以要具体。AI 不能直接改，只能提议（`propose_goal`），由你批准。

### 需求
一个需求是**一个对象，两个面**：

| 面 | 回答 | 落在哪 |
|---|---|---|
| 业务面 | 做什么、为什么、验收标准（AC-1、AC-2…） | `docs/specs/<名>/requirements.md` |
| 技术面 | 怎么做、用什么框架 | `docs/specs/<名>/design.md` |

两个面互相关联：例如业务面说「支持多端登录」，技术面说「用 sa-token 实现」，它们是同一个需求的两面，一起拆条目、一起做，而不是两个互不相干的东西。

- **人指定的技术要求：** 你可以在提交需求时直接写死技术方案，它是硬约束，架构师和员工不能推翻。
- **类型：** 功能（有业务面和技术面）/ 技术改进（升级框架、清理技术债，只有技术面）。
- **状态：** 待评估 → 已采纳 / 搁置 / 拒绝（后两者必须写原因）。已采纳的需求界面上还会显示阶段：编写规格 → 待拆分 → 实施中 → 已交付。
- **需求池：** 没勾「直接采纳」的需求先进池，由负责人在排期时评估。

### 计划与计划条目
**计划**是一组条目，是需求拆出来的具体工作，由负责人（项目经理视角）管理，偏「要做哪些事、谁依赖谁」。每个条目有：标题、说明、验收标准、**前置条目**、**等级**、指派的人、状态。

条目有几种**类型**（`kind`）：

| 类型 | 含义 |
|---|---|
| 设计 | 架构师出设计文档，只改 `docs/` |
| 规格 | 编写需求的业务/技术文档 |
| 实现 | 写代码 |
| Bug 修复 | 由 Bug 自动生成，指向那条 bug |
| 复测 | 由 Bug 自动生成，前置是对应的修复条目 |
| 其他 | 文档、测试、检查等 |

- **状态：** 提议中 → 待开始 → 进行中 → 已完成；也可能已阻塞或已取消。
- **就绪：** 前置都完成、不和进行中的条目改同一批文件、指派的人空闲、并发和预算允许，才会被派出去。计划页会写明每个条目在等什么。
- **来源：** 条目可以来自计划起草、需求拆分、Bug、定时器或评审意见，页面上都能看出来源。

### 等级（1–5）
按完成条目需要的推理和记忆来定，不是按工作量：

| 级 | 含义 |
|---|---|
| 1 | 机械改动：单个文件或函数，规格明确（改文案、改配置） |
| 2 | 简单：同一模块里的少量改动（补一组测试、加一个字段） |
| 3 | 中等：多个文件，要先读懂现有代码（新增一个接口、重构一个函数） |
| 4 | 较难：跨模块，涉及接口约定、错误处理或数据流 |
| 5 | 最难：架构取舍、并发与一致性、数据迁移、疑难 bug 定位 |

派活时选「能力上限不低于条目等级」里最低的那位。任务因能力不足失败，会自动升一级重派。

## 怎么安排：排期

**排期**是全部条目的先后顺序，分两个状态：

- **已排期：** 在顺序里有位置，自主推进只会派这一类。
- **未排期：** 刚产生、还没人安排的条目（Bug 生成的修复/复测、定时器、评审意见、新需求拆出的条目）。

**什么时候排：** 只要有未排期的条目（或待评估的需求），**且有人空闲**，自主推进就问负责人一次，一次处理全部——定先后、加前置、指派、评估需求、取消没价值的条目。这是唯一为排期新增的模型调用，没有未排期内容就不调用。

**顺序保证：** 前置条目一定排在依赖它的条目上面；排完后系统会校正，违反时界面上会标 ⚠。

**没有 AI 负责人或它回复不可用时**，按规则排：P0 bug 修复最先，P1 其次，其余按原顺序。

**你随时可以干预：** 上移/下移、退回未排期、手动排入、点「请负责人排期」立即排一次。

> 「计划」和「排期」不是一回事：计划回答**要做哪些事、谁依赖谁**；排期回答**什么时候先做哪件**。任务（员工的执行）在两者之后才发生。

## 谁来做：任务与合并

一个条目开始做时会创建一个**任务**：一个独立的 git worktree 加一条分支，员工只在里面改东西。做完经过验证、评审，再 squash 合并回主分支。放弃的任务保留分支和 WIP 提交，不丢改动。

**评审门：** 评审由负责人决定要不要开，另有规则兜底——改动达到 200 行或 8 个文件必须评审；改动很小（不超过 10 行且全是文档或注释）直接跳过；Bug 修复的改动里没有测试文件，也强制评审。其余由负责人看 diff 判断。

## Bug

Bug 是独立栏目，有自己的生命周期：

```
开放 ──开始修──▶ 修复中 ──修完──▶ 待复测 ──复测通过──▶ 已关闭
  │                                   └─ 没通过 → 重开（再生成修复 + 复测）
  └─ 无法复现 / 重复（必须写原因）
```

- **谁来记：** QA 测试时自己记；你也可以手动加。字段：严重程度、复现步骤、期望行为、实际行为、不应改变的行为、出自哪个条目。
- **谁来修：** 默认是做了「出处条目」的原开发。
- **优先级：** 按严重程度给默认值（阻断 P0、严重 P1、一般 P2），负责人可调。
- **记下之后系统自动（不调用模型）：** 生成「修复条目」和「复测条目」，复测依赖修复，都先进未排期，由排期决定什么时候让开发回来修。

## 定时器

项目内所有定时的事放在「定时器」栏目：

- **对齐会：** 保持目标对齐，防止多个 AI 开发久了各按自己思路偏离。会调用模型，所以有间隔。**它不参与排期。**
- **预置检查任务：** 依赖与安全检查、测试健康检查、文档一致性检查、每日构建冒烟。**默认全部关闭，由你决定是否启用。** 到点会在排期里建一个未排期条目（上一次还没做完则跳过）；应用没开着错过的时间点不补建。

## 自主推进（Autopilot）

负责人带着团队按排期连续干活，你旁观和纠偏。一个**批次**有预算（调用次数、时间），用完自动暂停，可设置自动续批次。批次里循环做的事：排期（有未排期且有人空闲时）→ 裁决议题 → 派就绪条目 → 验证 → 评审 → 合并 → 整理记忆 → 更新文档；条目失败时负责人调整计划（拆小、补前置、改派、换说明重试、取消）。应用重启时被打断的批次会自动接着做，但不会替你批准新计划。

**重装/重启会打断正在干活的员工**，被打断的任务会放弃（改动保留）并放回待开始。

## 讨论类：议题、评审意见、会议

- **议题：** 需要团队讨论并决定的事（多个可行方案、需求不明确）。员工可以提议；有 AI 负责人时由它裁决，裁决会自动记进「决策」文档。
- **评审意见：** 会议和评审里产生的意见。`[合并前]` 的会拦住所评审任务的合并；`[之后再说]` 的会自动变成未排期条目，不再单独调用模型整理。
- **会议：** 群 = 会议室，有对齐会、代码评审会等。会议是**只读模式**：员工只能看代码，不能改，也不能运行构建和测试。

## 记忆与文档

### 记忆
员工在工作中沉淀的经验和约定，分公司、项目、个人三层；每次只检索少量相关条目注入新任务。架构师设计文档里的「给团队的要点」会自动写成项目记忆。整理记忆时，与已定稿规格冲突的旧记忆会过期。

### 文档
文档页分两类，各自有**版本列表**（以 git 历史为准，每次合并算一个版本，点一行看那次的改动）：

| 类别 | 内容 | 谁写 |
|---|---|---|
| 项目文档（固定五份） | 架构、决策、风险、项目背景与约定、文档与代码规范 | 决策由议题裁决自动生成；其余由负责人/架构师维护，走和代码一样的分支与合并 |
| 规格文档（每个需求一份） | `requirements.md`（业务）+ `design.md`（技术） | 架构师（没有则开发） |

**项目文档 vs 规格文档：** 项目文档是长期背景，跨需求、随项目演进；规格文档是某一个需求的做什么/怎么做，需求交付后就是它的档案。**规格文档 vs 记忆：** 规格是完整的文档，给人和员工查；记忆是从中提炼的短条目，用来注入新任务。

## 会话与交接

员工的会话按「员工 + 项目路径」保存，上下文太大时自动换新会话。自建端点的员工换会话前会先写**交接摘要**，换后重新带上项目目标和记忆。

**角色交接：** 把项目里的某个角色（比如负责人）从一位员工交给另一位：原员工先写摘要，再执行交接；他手上进行中的任务自动放弃（改动保留），名下还没开始的活可选保留、交给新人或改回「未指定」。

## 事件与可观察性

几乎所有动作都会写入一条事件（数据库和 `events.jsonl`）。工作日志、「正在做什么」、人工介入中心、卡住检测、计划页的等待原因、公司总览都是从事件和表**读取时汇总**出来的，所以出了问题先看事件。

## 用量与预算

「用量」页统计调用次数、耗时、费用和每个会话的上下文。费用是 CLI 报告的等值估算；自建端点记 0。预算只统计「限制」的调用：订阅员工一定计入，自建端点上有「限制批次预算」开关。

## 成本原则

新增的概念（需求、Bug、排期、文档版本、定时器）基本都是**记录和视图**，不是新的模型调用。产生模型调用的只有：员工干活、负责人排期（仅当有未排期内容时）、裁决、评审、整理记忆、对齐会、规格文档的编写。
