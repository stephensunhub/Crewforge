# 核心概念

读完这篇，你应该能看懂界面里每个名词是什么、它们之间是什么关系。

```
公司 ── 员工（AI）──┐
  └── 项目 ── 成员（员工 + 项目角色）
            ├── 目标与硬性约束
            ├── 计划 ── 计划条目（设计 / 实现 …，有依赖和等级）
            ├── 任务 ── 一个条目对应一个 git worktree + 分支
            ├── 议题 / 行动项 / 会议
            └── 记忆 / 文档
```

## 员工

员工是一个 AI 工作者，本质是 Claude Code 或 GitHub Copilot 的 CLI 子进程，带一段身份说明和一个模型。员工之间互相独立：各有自己的会话、自己的工作区，不共享上下文，只通过群聊、议题、记忆和 git 协作。

- **名字和编号：** 名字可以改；每位员工有自增编号（界面里 `#N`），内部 ID 不变。
- **LLM 通道：** 本机订阅（用你已登录的 Claude Code / Copilot）或自建端点（如局域网里的 Ollama）。见 [连接本地模型](endpoints.md)。
- **能力上限（1–5）：** 这位员工最多能胜任几级的活。默认按模型自动给（本地模型 2，Haiku 3，Sonnet 4，Opus 和 Fable 5），可以手动改。

## 项目与角色

项目对应你磁盘上的一个 git 仓库。员工加入项目时有一个**项目角色**，同一位员工在不同项目里可以是不同角色：

| 角色 | 职责 |
|---|---|
| 负责人（lead） | 排计划、派活、裁决议题、判断是否评审、整理行动项和记忆、失败后调整计划 |
| 开发（developer） | 按计划条目写代码、跑测试 |
| QA | 验证和评审，不负责写功能 |
| 评审（reviewer） | 代码评审 |
| 架构师（architect） | 只做设计，不写代码，只改 `docs/` 下的 Markdown |

负责人可以是 AI，也可以是你自己。**有 AI 负责人时，决策权跟着它走**：行动项、议题裁决（含需求类和高风险）都由它定。你只保留：危险命令审批、删除项目、预算、批准目标变更。没有 AI 负责人时，待决定的事才交给你。

## 目标与硬性约束

项目级的一段文字，说明这个项目要达到什么、技术栈是什么、不做什么、怎么验收。每个新任务开始时都会带上它，所以要写得具体。AI 不能直接改它，只能提议（`propose_goal`），由你批准。

## 计划与计划条目

计划是一组条目，每个条目有：标题、说明、验收标准、**前置条目**（依赖）、**等级**、指派的人、状态。

- **状态：** 提议中 → 待开始 → 进行中 → 已完成；也可能已阻塞或已取消。
- **就绪：** 前置都完成、不和进行中的条目改同一批文件、指派的人空闲、并发和预算允许，才会被派出去。
- **设计条目：** 有架构师时，先出现设计条目（只给架构师）。设计合并后，负责人再按设计文档起草实现计划。

## 等级（1–5）

等级按完成条目需要的推理和记忆来定，不是按工作量：

| 级 | 含义 |
|---|---|
| 1 | 机械改动：单个文件或函数，规格明确（改文案、改配置） |
| 2 | 简单：同一模块里的少量改动（补一组测试、加一个字段） |
| 3 | 中等：多个文件，要先读懂现有代码（新增一个接口、重构一个函数） |
| 4 | 较难：跨模块，涉及接口约定、错误处理或数据流 |
| 5 | 最难：架构取舍、并发与一致性、数据迁移、疑难 bug 定位 |

派活时选「能力上限不低于条目等级」里最低的那位。任务因能力不足失败，会自动升一级重派。

## 任务与合并

一个计划条目开始做时，会创建一个**任务**：一个独立的 git worktree 加一条分支，员工只在里面改东西。做完后经过验证、评审，再 squash 合并回主分支。放弃的任务保留分支和 WIP 提交，不会丢改动。

评审由负责人决定要不要开，另有两条规则兜底：改动达到 200 行或 8 个文件必须评审；改动很小（不超过 10 行，且全是文档或注释）直接跳过，不调用负责人。其余情况由负责人看 diff 判断。

## 自主推进（Autopilot）

负责人带着团队按计划连续干活，你旁观和纠偏。一个**批次**有预算（调用次数、时间）；预算用完自动暂停，可以设置自动续批次。批次里循环做的事：裁决议题 → 派就绪条目 → 验证 → 评审 → 合并 → 整理记忆和行动项 → 更新文档；条目失败时负责人调整计划（拆小、补前置、改派、换说明重试、取消）。应用重启时被打断的批次会自动接着做，但不会替你批准新计划。

## 议题、行动项、会议

- **议题：** 需要团队讨论并决定的事（多个可行方案、需求不明确）。员工可以提议；有 AI 负责人时由它裁决。
- **行动项：** 会议和评审里产生的待办，负责人会持续整理：转成计划条目、驳回或保留。
- **会议：** 群 = 会议室。有对齐会（定期同步进度、检查目标）、代码评审会等。会议是**只读模式**：员工只能看代码，不能改，也不能运行构建和测试。

## 记忆与文档

- **记忆：** 员工在工作中沉淀的经验和约定，分公司、项目、个人三层；每次只检索少量相关条目注入新任务。架构师设计文档里的「给团队的要点」会自动写成项目记忆。
- **文档：** 项目 `docs/` 下的 Markdown。负责人维护的放在 `docs/crewforge/`：决策记录、已知问题、计划进度由数据生成，概览由负责人读代码撰写，走和代码一样的分支与合并流程。

## 会话与交接

员工的会话按「员工 + 项目路径」保存，上下文太大时自动换新会话。自建端点的员工换会话前会先写**交接摘要**，换后重新带上项目目标和记忆。

**角色交接：** 把项目里的某个角色（比如负责人）从一位员工交给另一位：原员工先写摘要，再执行交接；他手上进行中的任务会自动放弃（改动保留），名下还没开始的活可以选择保留、交给新人或改回「未指定」。

## 事件与可观察性

几乎所有动作都会写入一条事件（数据库和 `events.jsonl`）。工作日志、「正在做什么」、人工介入中心、卡住检测、计划页的等待原因都是从事件**读取时汇总**出来的，所以出了问题先看事件。

## 用量与预算

「用量」页统计调用次数、耗时、费用和每个会话的上下文。费用是 CLI 报告的等值估算；自建端点记 0。预算只统计「限制」的调用：订阅员工一定计入，自建端点上有「限制批次预算」开关。
