# 使用指南

按界面区域说明每个页面能做什么。名词解释见 [核心概念](concepts.md)，功能与典型流程见 [功能总览](features.md)。

## 界面布局

- **左侧栏：** 顶部是「公司」，下面是项目列表（项目多时有搜索框）；底部是「模型」「用量」「设置」。侧栏可以收成窄条。
- **右上角：** 小铃铛，汇总需要你处理的事（审批、议题、卡住提示等）。
- **项目页：** 顶部一排标签页：职责、导入、群聊、需求、计划、排期、任务、Bug、议题、会议、评审意见、定时器、成员、记忆、文档。

## 公司页

- **总览：** 每个项目一张卡：完成度、进行中的活、bug 数、最近一批自主推进、近 7 天调用数，以及需要你关注的原因（阻塞、bug 待修、待确认的条目、有活但自主推进没在跑……）。点卡片进计划页；下方列出即将触发的定时任务。
- **员工：** 新建、编辑、改名、归档员工；选择 LLM 通道和模型；设置能力上限（自动或 1–5）；编辑身份说明。
- **项目：** 「＋ 新建 / 导入项目」。已有代码的目录会走导入流程；全新项目不要勾「已有项目」。
- **公司记忆与简介：** 公司级的约定，所有项目共享。

## 项目页各标签

| 标签 | 用途 |
|---|---|
| 职责 | 开始 / 暂停 / 停止**自主推进**，设置每批次预算和自动续批次；看当前批次状态 |
| 导入 | 已有项目的只读扫描、测试基线，确认后进入团队维护阶段 |
| 群聊 | 项目的主时间线：你发消息（`@员工` 可以直接派活）、员工汇报、审批请求；支持 Markdown |
| 需求 | 需求池（待评估）和已采纳的需求：业务面和技术面写在同一份规格里，采纳后写规格、拆条目 |
| 计划 | 项目目标与硬性约束；计划条目（依赖、等级、指派、等待原因）；目标变更提议 |
| 排期 | 全部条目的先后顺序表：已排期 / 未排期，显示排入时间、前置、状态、阻碍、触发原因；可上移下移、退回未排期、「请负责人排期」 |
| 任务 | 每个任务的分支、改动文件、diff、合并预检；合并、放弃 |
| Bug | 独立的 bug 栏目：QA 在测试时记，你也可以添加；谁开发的谁修，修完复测，复测通过才关闭 |
| 议题 | 需要决定的事；有 AI 负责人时由它裁决，升级给你时在这里处理 |
| 会议 | 对齐会、评审会的发言和纪要；你也可以参与发言 |
| 评审意见 | 会议和评审里产生的意见：`[合并前]` 的会拦住所评审任务的合并；`[之后再说]` 的会自动变成「排期」里的未排期条目 |
| 定时器 | 对齐会和预置的检查类定时任务（默认全部关闭，由你启用） |
| 成员 | 项目成员和角色；添加成员；**交接…**（把角色交给别人） |
| 记忆 | 项目记忆：查看、编辑、确认 |
| 文档 | 主分支 `docs/` 下的 Markdown，只读 |

## 上线之后：需求、Bug、排期、文档

这些都落在同一个模型里：**需求**（做什么、怎么做）→ **计划条目**（拆出来的具体工作）→ **任务**（员工的一次执行）。Bug 是独立栏目，它和定时器、评审意见产生的活都先进「未排期」，由**排期**决定先后。

**需求。** 在「需求」标签提交：一个需求同时有业务面（做什么、为什么、验收标准）和技术面（怎么做、用什么）。有明确的技术要求就填「人指定的技术要求」，它是硬约束，架构师和员工不能推翻。提交时可以勾「直接采纳」，不勾就进需求池，由负责人在排期时评估（采纳 / 搁置 / 拒绝，后两者必须写原因）。采纳后：架构师（没有就由开发）依次写业务需求和技术方案两份文档（`docs/specs/<名>/requirements.md`、`design.md`，只能改文档）；定稿后负责人按规格拆出实现条目，条目的任务提示词会指向规格，验收以其中的验收标准（AC-n）为准。需求变了点「修订」，员工在原文档上修改并追加变更记录，负责人只为变化的部分拆新条目。纯技术改进（升级框架、清理技术债）选「技术改进」类型，只有技术面。

**Bug。** QA 测试或评审发现问题，会自己用团队工具记到「Bug」栏目；你也可以手动添加（复现步骤、期望与实际行为、不应改变的行为、出自哪个条目）。记下之后系统（不调用模型）立刻：按严重程度给默认优先级（阻断 P0、严重 P1、一般 P2），建一个**修复条目**（指派给做了出处条目的原开发）和一个**复测条目**（有 QA 给 QA，没有 QA 给负责人），都进未排期。修复条目开始后 bug 是「修复中」，完成后是「待复测」，复测条目完成才「已关闭」；复测没通过用「重开」，会再安排修复和复测。改动里没有测试文件的修复会被强制评审。

**排期。** 「排期」标签是全部条目的先后顺序表。**只要有未排期的条目（或待评估的需求），且有人空闲，自主推进就问负责人一次**，一次处理全部：定先后顺序、加前置、指派、评估需求、取消没价值的评审意见条目。负责人回复不可用或项目没有 AI 负责人时，按规则排（P0 bug 插最前，P1 排在普通条目前，其余按原顺序追加）。自主推进只派「已排期」的条目。自主推进没在跑时，后台每 5 分钟也会查一次，同样给未排期的条目排（同一批条目只排一次，有变化或隔一小时才再排；负责人正在忙就等下次）。你可以上移 / 下移、退回未排期、手动排入，也可以点「请负责人排期」立即排一次。对齐会不参与排期，只管防止大家偏离目标。

**文档。** 「文档」标签分两类：**项目文档**是长期背景，固定五份——架构、决策（议题裁决自动生成）、风险、项目背景与约定、文档与代码规范；**规格文档**是每个需求一份（业务 + 技术）。每份文档都有**版本列表**，以 git 历史为准：每次合并算一个版本，点一行看那次的改动。

**定时器。** 「定时器」标签里有对齐会，和预置好的检查类定时任务（依赖与安全检查、测试健康检查、文档一致性检查、每日构建冒烟），默认全部关闭，勾一下启用。到点会在排期里建一个未排期的条目；应用没开着错过的时间点不补建。

## 常见操作

### 新建一个项目并让团队开工

见 [快速开始](getting-started.md)。要点：目标里写清技术栈、不做什么、验收标准。

### 给员工派一个临时任务

在「群聊」里 `@员工名 要做的事`。员工在自己的 worktree 里做，做完后在「任务」页评审、合并。

### 审批

员工要做越界的事（写工作区之外、危险命令）时，会弹审批：允许、拒绝，或「允许并加入白名单」（网络域名）。沙箱内的普通命令自动放行。

### 改项目目标

你可以直接在「计划」页改。AI 想改目标时只能提议，你在这里批准或驳回（可以修改后批准）。

### 处理批次的「等你处理」

先看提示里的原因，再看「计划」「议题」「行动项」「任务」。处理后点「再开一个批次」。

### 换负责人 / 角色交接

「成员」页 →「交接…」：选要交接的角色和接手的员工，原员工先写摘要，再执行交接。原员工进行中的任务会自动放弃（改动保留）；他名下还没开始的活可选：不动、交给新人、改回「未指定」。新负责人在下一个批次开头会做一次接手复盘：补等级、按能力重新分配。

### 看用量

左下角「用量」：按员工、模型、用途汇总调用次数、耗时、费用；也能看到每个会话的上下文占用。

### 全局设置

左下角「设置」：沙箱网络白名单、会话上下文上限、是否阻止 Mac 在批次运行时休眠等。

## 命令行

`crewforge` 命令行用来验证核心链路和排错：

```sh
cargo run -p crewforge-cli -- employee list
cargo run -p crewforge-cli -- events 50
cargo run -p crewforge-cli -- tasks <项目目录>
cargo run -p crewforge-cli -- cost 7
```

完整子命令见 `crates/cli/src/main.rs` 开头的注释。数据目录用环境变量 `CREWFORGE_HOME` 指定。
